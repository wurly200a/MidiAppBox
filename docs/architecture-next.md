## 0. レビュー観点(最初に読むこと)

> **「この API 語彙は要件 1〜5 を通しても増えない」が層の切り方の検証である。**

層を正しく切れていれば、5 つのアプリ要件(高精度メトロノーム / 楽曲メトロノーム /
SMF インポート / 2trk シーケンサー+録音 / ドラムマシン)をすべて通しても、
Host API の語彙は増えないはずである。増えるなら層の切り方が間違っている。
検証結果は `docs/hostapi-next.md` の「アプリ要件突き合わせ表」にある。

レビューで特に見てほしい点は §11 に列挙した。

## 1. 現行アーキテクチャの限界(なぜ改訂するか)

現行の方針(下記 3 点)は維持する。これらは有効なまま:

- タイミングクリティカル層(オーディオ出力、描画ドライバ、将来の FM 音源)は
  ネイティブホスト側。WASM アプリはロジックのみを持ち、ホスト API を叩く。
- WASM アプリは Rust / `wasm32-unknown-unknown`(WASI 不使用)。
- 実機ランタイムは WAMR。まず interpreter で動かし、AOT は後続フェーズ。

改訂が必要なのは、**ホスト側に音楽時間軸が存在しない**ことに起因する 3 つの問題:

1. **テンポの二重管理**: MIDI Clock のテンポは「クリック予約の間隔」から逆算して
   いる(`hostapi_midi_send` の Start 副作用 + `Midi_NotifyBeatScheduled`)。
   音楽的なテンポがどこにも一次情報として存在しない。
2. **毎拍の位相リセット**: 上記の逆算のため毎拍 `esp_timer_stop` →
   `start_periodic` で再アームしており、120bpm でマージンが 8µs しかない。
   Phase 9c で**約 61% の拍でクロックが 1 発欠落する**ことを送受信双方の
   データと対照実験で実証済み。
3. **小節・拍・ループ・テンポマップが表現できない**: セクション構成や途中テンポ
   変更を持つ曲、SMF、録音の打刻といった要件が現行の語彙では表現できない。

## 2. 層構成(L0〜L3)

```
L3 (WASM)  曲構造・SMF パース・UI(A メロ/B メロ/サビ、ソング構成)
L2 (WASM)  先読み供給(tick 付きイベントを L0 へ、1〜2 小節先まで)
─────────────────── Host API 境界 ───────────────────
L1 (native) 音楽時間軸: テンポ/拍子マップ、transport、ループ、
            MIDI クロック生成(グリッドから直接生成)
L0 (native) tick 順イベントキュー + Clock Authority + ポート抽象
            (port: DIN-OUT / USB-MIDI / 内蔵音源 / click)
```

| 層 | 責務 | 責務でないもの |
|---|---|---|
| **L3** | 曲構造、SMF パース、UI、ユーザー操作の解釈 | 実時間の管理、送出タイミング |
| **L2** | 「今どこまで供給済みか」を見て、horizon まで tick 付きイベントを書く | 実時間、ジッタ補償 |
| **L1** | tick ↔ host 時刻の写像(テンポマップ)、transport 状態、ループ写像、MIDI クロックのグリッド生成 | ポート固有の送出規律 |
| **L0** | tick 順キュー、ワンショット 1 本のディスパッチ、Clock Authority、ポート抽象と送出規律 | 音楽的意味の解釈 |

**境界の原則**: Host API 境界(L1/L2 間)を越えるのは **tick 付きのイベント**と
**テンポマップの変更**だけである。実時間(µs)は境界を越えない。唯一の例外は
録音打刻の変換 `time_us_to_tick` で、これは受信側の µs を tick へ引き込むためにある。

## 3. Clock Authority(レートマスターの決定)

系内の全時刻変換を通す唯一のモジュール。`(sample_count, host_us)` の対応を維持する。

### レートマスター = I2S 出力のサンプルカウント

**根拠(P10-1、go 判定)**:

| 項目 | 実測値 |
|---|---|
| 取得手段 | `i2s_channel_register_event_callback` の `on_sent`(enable 前に登録) |
| 粒度 | 960 バイト = 240 フレーム = **5442.2µs**(理論値と一致) |
| 打刻間隔ジッタ | σ 0.6〜1.0µs、最悪 ±62µs |
| 線形補間誤差 | 平均 0.2µs、**負荷込み最悪 ±62µs**(判定基準 ±500µs の 1/8) |
| 既存経路への干渉 | なし(A/B/A 対照で確認) |

**決め手となった性質**: `on_sent` は**データ未供給時(無音)もフリーランで
発火し続ける**(`auto_clear` 有効時、ドライバがゼロを送出するため)。したがって
再生していない間もサンプルカウントは単調増加し、レートマスターとして途切れない。

**採らなかった案 (a) 書き込み累計**: 累計自体は正確だが、write が発生している間しか
進まず(無音区間で停止)、ブロッキング write の戻りも消費と疎結合(実測 max 45〜52ms)。
レートマスターには使えない。

### 対応更新は固定比でよい

**根拠(P10-2)**: アイドル約 7 分 × 2 回で実効 fs = 44100.0000 Hz、公称比
**−0.00 ppm**、30 秒窓の変動幅 ≤0.06 ppm。算術的にも裏付けがある:
I2S も esp_timer も同一の 40MHz 水晶から派生し、分数分周が 44.1kHz の厳密比
(MCLK = 160MHz × 441/6250 = 256 × 44100)を達成するため、丸め誤差は原理的にゼロ。

したがって **PLL 的な逐次推定は不要**。公称 44100 の固定換算 + 起動時オフセットで足りる。
系内誤差は補間誤差(±62µs)に支配される。

### 環境差(重要)

これは「オーディオクロックとタイマクロックが同一水晶」という ESP32-S3 実機の
性質である。**ブラウザホスト(Phase A)等、両者が別系統の環境では逐次推定が
必要になる。** Clock Authority のインタフェースは固定比・逐次推定のどちらの実装も
受け入れられる形にしておくこと(対応の更新点を 1 箇所に閉じ込める)。

また 44.1kHz 以外(22.05kHz 等)へ切り替える場合は換算係数の切替が要る。
44.1kHz 以外で同様の厳密比が成るかは未測定。

## 4. tick 座標系

- **内部 PPQN = 960**、tick は **u32**。
- 960 の根拠: 24 で割り切れる(MIDI Clock 1 発 = 40 tick の整数)、SMF 最頻の
  480 から ×2 で無損失変換、16 分音符 = 240 tick、3 連符・5 連符も整数化しやすい。
- u32 の根拠: 4/4・120bpm で 1 小節 = 3840 tick。u32 の上限まで約 1.1M 小節 ≒
  連続 25 日。実用上あふれない。
- **tick は楽曲時間であって実時間ではない。** 実時間への写像はテンポマップが持つ。

## 5. MIDI クロックのグリッド生成

- **40 tick(= 960/24)ごとのグリッドから直接生成する。**
- Phase 9c の根本原因だった `period_ms` 経由の相対再アーム経路は**廃止**する。
  `Midi_NotifyBeatScheduled` / `Midi_NotifyBeatFired` によるテンポ逆算も廃止。
- クロックは L1 がテンポマップから生成するので、アプリは何もしなくてよい
  (テンポを二重に持たない)。

**根拠(P10-3)**: 絶対時刻グリッド(予定時刻 + 20833µs)のワンショット連鎖で、
アイドル ×2・loopback ×2・mp3 再生+タッチの最悪負荷 ×2 の全条件・30,268 発において
**クロック欠落 0・追いつき(late)0**。TX 発火偏差は最悪 104µs、受信間隔の平均は
20833.0µs ちょうど。9c の外れ値 155〜185 件 / BPM の二峰性は完全に消失した。

## 6. L0 ディスパッチャ

- **キューのソートキーは musical tick**(µs ではない)。
- ディスパッチャは「次に期限が来るイベントの tick」をその時点のテンポマップで
  host 時刻に変換し、**esp_timer ワンショット 1 本**で arm する。
- 再アームは**絶対時刻グリッド基準**(前回の予定時刻 + 間隔)。発火時刻からの
  相対加算にしない(累積ドリフト防止。P10-3 で実証済みの方式)。
- **テンポ変更時に積み直し(flush)が不要**になる。キューは tick 順のままで、
  変換係数だけが変わるため。これが「ソートキーを tick にする」ことの主目的。
- 発火偏差の系統分(実測 16〜26µs、esp_timer タスクのディスパッチ遅延)は
  定数オフセットなので、予定時刻をその分前倒しして補正してよい。

### イベントレイアウト(16 バイト)

```c
typedef struct {           /* 16 bytes, align 4, リトルエンディアン */
    uint32_t tick;         /* 発火する playback tick(絶対) */
    uint8_t  port;         /* HOSTAPI_PORT_* */
    uint8_t  status;       /* MIDI ステータスバイト、または HOSTAPI_SEQ_OP_* */
    uint8_t  data1;
    uint8_t  data2;
    uint32_t param;        /* op 依存(tone slot 等)。MIDI イベントでは 0 */
    uint32_t _reserved;    /* 常に 0。将来拡張(可変長イベントのハンドル等) */
} l0_event_t;
```

**アプリが `seq_write` に渡す `hostapi_seq_event_t` と同一レイアウトにする。**
境界での変換コストがゼロになり、ABI の記述も 1 箇所で済む。

同一 tick 内の順序は **`seq_write` に書かれた順**とする(キューは安定順序を保つ)。
実装は tick 昇順の挿入ソート配列を推奨する(L2 からはほぼ昇順に届くので挿入は
末尾追記に近く、深さ 256 なら memmove も十分速い)。

## 7. ポート抽象と送出規律

`port` はイベントの出力先を表す enum。**API 語彙を増やさずに出力先を増やせる**
ことが、この抽象の目的である(ドラムマシン要件が port 値の追加だけで通る)。

| port | 内容 | 状態 |
|---|---|---|
| `DIN_OUT` | 物理 MIDI OUT(UART1、GPIO18) | 実装済み(Phase 8a) |
| `USB_MIDI` | USB-MIDI | 将来 |
| `SYNTH` | 内蔵音源(FM / サンプラー) | 将来(本フェーズは port 抽象の設計のみ) |
| `CLICK` | トーンパレット(既存 `tone_define` のスロット) | 実装済み(Phase 7C) |

### DIN-OUT の送出規律(P10-5 の結果)

MIDI 規格上、システムリアルタイムバイト(0xF8 等)は他メッセージのバイト列途中に
割り込んでよい。実測でこれが ESP32 の UART ドライバ構成で成立することを確認した。

**確認できたこと**:

- **バイト列の完全性は完璧**: 0xF8 を挟んでも 24,043 件のノートメッセージが
  1 バイトも欠落・化けせず、0xF8 を除いた列は送信列と完全一致。
- **`uart_write_bytes` で足りる。TX FIFO 直叩きは不要。** 0xF8 を書く瞬間の
  FIFO 占有量は平均 0.05 バイト・最悪 2 バイト、換算挿入遅延は**平均 16µs・
  最悪 640µs**(MIDI 1 バイト時間 320µs と同オーダー)。
- **TX リングバッファ(`tx_buffer_size>0`)も使わない。** 現行の
  `tx_buffer_size=0` を維持する。リングバッファを挟むと割り込み地点の制御が
  効かなくなるため。
- SL MK3 実機でも、10ms 間隔のノートを受けながらクロック検知テンポが安定
  (ユーザー目視確認)。

**規律(実装で守ること)**:

1. TX FIFO は 128 バイト = MIDI 換算 **41ms** ぶんある。FIFO は FIFO なので
   **既に積まれたバイトの前には原理的に割り込めない**。0xF8 の遅延は
   「書く時点の FIFO 占有バイト数 × 320µs」に等しい。
2. したがって **大きなバーストを 1 回の `uart_write_bytes` で流し込まない**。
   SysEx(Phase 8c で 302 バイトを実測)を一括で書くと、その後のクロックが
   最大 41ms 待たされる。
3. 小さなメッセージ(3〜4 バイト)は一括書き込みでよい(実測で FIFO 占有が
   最悪 2 バイトに収まった)。大きなメッセージは小さく分割して書き、
   **バイト境界ごとにリアルタイムキューを確認して差し込む**。
4. リアルタイムバイト(0xF8/0xFA/0xFB/0xFC 等)は専用の最優先キューに置き、
   ポートの送出ループが各バイト境界で最初に確認する。

## 8. 入力(録音)経路と打刻精度

録音は `hostapi_midi_recv` で生バイト + host µs を受け、`time_us_to_tick` で
tick に引き込む。パースは従来どおりアプリ(L3)の責務。

**打刻精度の限界(P10-5 で定量化)**: `rx_task` は 1 回の UART イベントで届いた
複数バイトに**同一のタイムスタンプ**を付ける。連続受信時はイベント 1 件が
3〜4 バイトを運ぶため、個々のバイトの見かけ時刻が最大 **≈1.3ms** ずれる。

- クロック単独受信(バイト間に idle gap がある)なら σ 16µs と正確。
- ノートが継続的に流れると σ 1.19ms まで劣化する。これは**受信側の計測分解能**
  の問題であって、送信ジッタではない(ペーシング実装で FIFO 占有が証明可能に
  ゼロでも同じ σ が出たことで切り分け済み)。

**補正**: ボーレートが既知(31250bps = 320µs/バイト)なので、N バイトを運ぶ
イベントの i 番目(0 始まり)の到着時刻は

```
t_i ≈ T - (N - 1 - i) × 320µs      (T = ホストが打った代表時刻)
```

と復元できる。**この補正は L0 の入力経路に入れる**(`time_us_to_tick` に渡る前に
補正済みの µs にする)。既存の `hostapi_midi_recv` のタイムスタンプにも同じ補正を
適用してよいが、ABI 上の意味が変わるため互換性の判断は実装フェーズで行う。

**設計上の区別**: 送信グリッド精度(~100µs)と受信打刻精度(~ms 級のテール)は
別物である。録音のクオンタイズ設計ではこの非対称性を前提にすること。

## 9. メモリ配置方針

**根拠(P10-4)**: WASM アプリ実行中の internal RAM は free 29〜31KB、
**largest free block は 13〜14KB** しかない(9c で判明した逼迫水準と一致)。

| 項目 | 方針 | 根拠 |
|---|---|---|
| L0 キューの配置 | **internal RAM の静的 BSS** | 恒久物は静的確保に(6B/7B-fix の教訓)。ヒープから取ると largest free block を食い潰し WASM の linear memory 確保を壊す(9c で実証済みの失敗モード) |
| L0 キューの深さ | **4KB = 256 イベント** | 9c の実績: native 側に 12KB 追加で WASM 起動失敗、4KB は問題なし。8KB は未検証 |
| PSRAM | **使わない** | P10-4: 8MB octal を搭載しているが、有効化すると SD 初期化の SDMMC プローブで TG1WDT リブートループに陥る。ドロップイン変更ではない |
| キュー操作のコスト見積 | 定常 ~360ns/op、**負荷時 ~1.4µs/op** | P10-4 の 16B ランダムアクセス実測(mp3 再生中に 3.8 倍へ跳ねる回を観測)。ISR/タイマコールバック内の操作はこの最悪値を見込む |

### 256 イベントが与える先読み horizon

4/4・16 分音符グリッド・ノート on/off で 2 イベント/音として:

| 同時発音数 | 1 小節あたり | 256 イベントで賄える長さ |
|---|---|---|
| 1 声部 | 32 イベント | 8 小節 |
| 2 声部 | 64 イベント | 4 小節 |
| 4 声部 | 128 イベント | **2 小節** |

設計候補の L2 horizon「1〜2 小節先まで」は 4 声部でちょうど収まる。
MIDI クロックはグリッドから直接生成するため**キューを消費しない**(設計判断 4)
ことが、この収まりに効いている。

より深い horizon や多声部が必要なら 8KB(512 イベント)への拡張を検討するが、
**WASM linear memory 確保への影響を再検証すること**(9c: 12KB で破綻、4KB は安全、
8KB は未検証)。

## 10. 既存アーキからの移行方針(Phase 11 以降の実装順序案)

既存アプリ(demo / bars / mp3player / metronome / clicktest / midi_loopback)の
回帰を壊さないことを各ステップの完了条件とする。

| # | ステップ | 完了条件 |
|---|---|---|
| 1 | L0/L1 を native に実装(既存経路と並存、まだ誰も使わない) | ビルドが通り、既存アプリの挙動が不変。static 4KB 追加後も WASM 起動 OK(largest free block 確認) |
| 2 | Host API 追加(`transport_*` / `tempomap_*` / `seq_*` / `time_us_to_tick`) | 既存 API のシグネチャ・挙動は不変。Linux ホストにも同時実装 |
| 3 | **metronome を新 API で書き直す** | midi_loopback の E1 統計で 9c 実測と前後比較。外れ値 0・BPM 単峰を確認 |
| 4 | 既存クリックスケジューラを L0 経由に置換(`hostapi_click_schedule` を L0 の薄いラッパにする) | clicktest / metronome(旧版)の回帰なし。内部だけが切り替わる |
| 5 | `hostapi_midi_send` の Start/Stop 副作用(クロック生成トリガ)を削除 | テンポの二重管理が消える。midi_loopback で確認 |
| 6 | ポート抽象の拡張(内蔵音源) | 別フェーズ。API 語彙は増えないことを確認 |

ステップ 3 が本改訂の価値を最初に検証する地点である
(**9c の欠落 61% → 0 件**を実アプリで再現できるか)。

## 11. レビューしてほしい論点

1. **ループの tick 表現(§6 と `hostapi-next.md` §transport)**: L0 のソートキーを
   単調増加の playback tick にするため、ループの巻き戻しは L1 が
   「playback tick → song tick」の写像として持つ案にした。L2 は絶対の
   playback tick で供給し続ける。この切り方でよいか。
2. **PSRAM を使わない前提**: 8MB 搭載していながら使わない設計にしている。
   L0 キュー 256 イベントで足りるかは §9 の horizon 表を見て判断してほしい。
3. **`hostapi_click_schedule` / `hostapi_tone_schedule` の非推奨化**: 移行の
   ステップ 4 で内部を L0 に載せ替え、API 自体は当面残す案にした(既存アプリの
   回帰保護)。いつ削除するか。
4. **受信打刻の補正を既存 `hostapi_midi_recv` にも適用するか**: 精度は上がるが
   ABI 上の意味(「ホストが受信直後に打った時刻」)が変わる。
5. **44.1kHz 固定の前提**: MP3 再生で 22.05kHz へ切り替わる経路があるため、
   Clock Authority の換算係数切替を L0 のどこで扱うか。

## 12. 数値の根拠表

設計中のすべての定数と、その実測または計算根拠。
