# Phase 10: 新アーキテクチャ先行調査と設計書作成(実装なし)

## 目的

ホスト側に音楽時間軸を持たせる新アーキテクチャ(下記「設計候補」)の**成立条件を
実測で確認し、設計書として文書化する**。本フェーズの成果物は調査結果と設計書であり、
**新アーキテクチャの実装は一切行わない**(実装は承認後の Phase 11 以降)。

背景: Phase 09c(`docs/results/phase09c.md`)で、現行の MIDI Clock 生成
(毎拍の位相リセット、マージン `(period_ms*1000) mod 24` µs ≤ 23µs)が
クロック欠落の根本原因であることが確定した。恒久対策は場当たり的な修正ではなく、
ホストが音楽時間軸を持つ構造への移行で行う、というのが確定済みの方針である。

## 位置づけと前提

- Phase 09c の結果はすべて有効な前提として使ってよい(09b とは異なり、
  再現性確認済み)。特に以下の実測値は本フェーズの設計判断の入力である:
  - esp_timer periodic の定常ジッタ: 除外後σ 83〜86µs、min/max -635〜+1224µs
  - 実機の一般ヒープ largest free block: 実測約 15KB(逼迫)
  - native 側静的バッファの追加が WASM linear memory 確保に影響する(教訓)
- `wasm-apps/midi_loopback/` の E1 統計機能(ヒストグラム・ロバスト統計・
  外れ値リスト・BPM 分布・STOP 時のシリアルダンプ)は恒久機能として存在し、
  本フェーズの計測に流用してよい。

## 設計候補(本フェーズで検証する仮説。確定仕様ではない)

以下はユーザーとアーキテクチャ議論で合意済みの候補設計である。調査項目
P10-1〜P10-5 はこの候補の成立条件を検証するためにある。**調査結果が候補と
矛盾した場合は、候補に合わせて結果を曲げず、矛盾を報告して停止すること。**

### 層構成

```
L3 (WASM)  曲構造・SMFパース・UI(Aメロ/Bメロ/サビ、ソング構成)
L2 (WASM)  先読み供給(tick付きイベントを L0 へ、1〜2小節先まで)
─────────── Host API 境界 ───────────
L1 (native) 音楽時間軸: テンポ/拍子マップ、transport、ループ、
            MIDI クロック生成(グリッドから直接生成)
L0 (native) tick順イベントキュー + Clock Authority + ポート抽象
            (port: DIN-OUT / USB-MIDI / 内蔵音源 / click)
```

### 主要な設計判断(候補)

1. **時間座標系**: オーディオ出力のサンプルカウントをレートマスターとし、
   esp_timer µs との対応 (sample_count, us) を単一の Clock Authority
   モジュールが維持する。系内の全時刻変換はこのモジュールだけを通す。
2. **L0 キューのソートキーは musical tick**(µs ではない)。ディスパッチャは
   「次に期限が来るイベントの tick」をその時点のテンポマップで host 時刻に
   変換し、esp_timer **ワンショット** 1 本で arm する。テンポ変更時に
   積み直し(flush)が不要になる。
3. **内部 PPQN = 960**、tick は u32。24 で割り切れる(MIDI Clock が整数 tick)、
   SMF 最頻の 480 から ×2 無損失変換。
4. **MIDI クロックはグリッド(40 tick = 960/24 ごと)から生成**。09c の
   根本原因だった `period_ms` 経由の相対再アーム経路は廃止。
5. **DIN OUT の送出規律**: MIDI 規格上、システムリアルタイムバイト(0xF8 等)は
   他メッセージのバイト列途中に割り込み可。ポート内送出でこれを利用する。

## ゲート(必須)

- 本フェーズでは Host API / ABI を変更しない。調査用コードはすべて
  `#ifdef PHASE10_xxx_TEST` ガード内に置き、各調査の検証完了後に削除する
  (`main` の挙動は本フェーズ開始前と同一に保つ)。
- **P10-1 は go/no-go ゲート**である。no-go 判定(下記基準)の場合、
  P10-2 以降のうちサンプル軸前提の項目は実施せず、判定根拠を報告して
  停止し、ユーザーの判断を仰ぐこと。
- 設計書は「調査結果の反映 → ユーザーレビュー → 承認」を経て確定する。
  承認前に実装フェーズの作業(新 API の実装、既存スケジューラの置換)を
  始めないこと。

## 調査項目(P10-1 から順に実施。P10-4 のみ任意のタイミングで実施可)

各項目とも、計測値の読み取りはカメラ静止画に頼らず、シリアルログ
(`captures/phase10/` 配下)から取得すること(09c と同方針)。native 側に
計測用の静的バッファを追加する場合は、09c の教訓に従い**追加前後で
`heap_init` の RAM 報告と largest free block を確認**し、WASM の起動失敗を
誘発しないサイズ(目安: 合計 4KB 以下)に収めること。

### P10-1: I2S 再生位置(消費済みサンプル数)の取得可能性 【go/no-go ゲート】

**目的**: Clock Authority がサンプル軸をレートマスターにできるかの成立条件を
確認する。「DAC が実際に消費したサンプル数」に相当する値を、どの粒度・
どのコスト・どの信頼度で取得できるかを実測する。

**調査方法**(両方試し、比較する):

- (a) **書き込み累計 − 未消費推定**: `i2s_channel_write` した累計サンプル数を
  アプリ側でカウントし、DMA バッファ総量との関係から消費済み数を推定する
  方式が現行ドライバ(ESP-IDF v5.5 の i2s std モード)で成立するか。
  ブロッキング write の戻りタイミングと消費の関係を確認する。
- (b) **`on_sent` コールバック**: `i2s_channel_register_event_callback` の
  送信完了コールバックで DMA バッファ完了を数える方式。コールバック内で
  `esp_timer_get_time()` を打刻し、(累計サンプル数, us) のペアを
  リングバッファに記録する。

**取得データ**:

1. 取得粒度(= DMA バッファ 1 個分のサンプル数と、その時間換算)
2. (b) のコールバック打刻の間隔の統計(midi_loopback E1 と同形式:
   ヒストグラム・ロバスト統計)。理論値(バッファ長 / fs)からの偏差と σ
3. 打刻ペア (sample_count, us) を線形補間したとき、補間誤差がどの程度に
   収まるか(隣接ペアの中点で実測 us と補間 us を比較)
4. 現行の click 再生経路(audio.cpp)との干渉有無(コールバック追加で
   既存動作が変わらないこと)

**go/no-go 判定基準**:
- go: (a)(b) いずれかで単調増加のサンプルカウントが取得でき、線形補間後の
  時刻対応誤差が **±500µs 以内**(MIDI 1バイト時間 320µs と同オーダー)に
  収まる見通しが立つこと
- no-go: 粒度・ジッタ・ドライバ制約のいずれかで上記が満たせない場合。
  この場合「esp_timer マスター + 音側補正」への転換が必要になるため、
  実測データを添えて報告・停止する

### P10-2: 実効サンプルレートの ppm 計測(P10-1 が go の場合のみ)

**目的**: 公称 fs と実効 fs のずれ(分数分周の丸め)を数値化し、
Clock Authority の対応更新方式(固定比で足りるか、逐次推定が要るか)を決める。

**方法**: P10-1(b) の打刻ペアを **5 分以上**継続取得し、
`実効fs = Δsample / Δus × 10^6` を全区間および 30 秒窓ごとに算出。

**取得データ**: 公称比 ppm(全区間)、30 秒窓ごとの ppm の変動幅
(温度等による揺らぎの有無)、および同一条件 2 回での再現性。

### P10-3: ワンショット再アーム方式のジッタ実測

**目的**: L0 ディスパッチャの候補方式(esp_timer ワンショット →
発火 → 次イベント時刻で再 arm)の到達精度を、最悪負荷下で確認する。
09c の σ83〜86µs は periodic の値であり、ワンショット連鎖では
再アーム処理の分だけ悪化しうる。

**方法**: `PHASE10_ONESHOT_TEST` ガード内に、20833µs 間隔で
「ワンショット発火 → 0xF8 送出 → 次回時刻(絶対時刻基準: 前回の
*予定*時刻 + 20833µs)で再 arm」を繰り返す試験コードを実装。
**次回時刻は発火時刻からの相対ではなく予定時刻からの絶対加算**とする
(累積ドリフトを防ぐ方式そのものを試験する)。ループバックで
midi_loopback(E1 統計)により受信側から計測する。

**負荷条件**(各 120 秒、2 回ずつ):
1. アイドル(ランチャー画面のまま)
2. 最悪負荷: mp3player で MP3 再生中 + ユーザーに依頼して断続的な
   タッチ操作(LVGL 描画 + i2s_write + タッチ割り込みの複合)

**取得データ**: E1 統計一式。特にテール(除外後 min/max)が 09c の
periodic 実測(-635〜+1224µs)からどう変わるか。外れ値(欠落)が
0 件であること(ワンショット方式で欠落が出るならその条件)。

### P10-4: メモリ監査(任意のタイミングで実施可)

**目的**: L0 キュー(候補: 16B/イベント)の配置先と深さ、および L2 の
先読み horizon の上限をメモリ実測から逆算できる状態にする。

**方法・取得データ**:
1. `heap_caps_get_info` / `heap_caps_get_largest_free_block` を
   `MALLOC_CAP_INTERNAL` / `MALLOC_CAP_SPIRAM` それぞれで、起動直後・
   ランチャー表示中・mp3player 再生中・midi_loopback 実行中の 4 時点で記録
2. sdkconfig 上の PSRAM 有効/無効、サイズ、キャッシュ設定の確認と、
   現状 PSRAM を使っているコンポーネント(LVGL バッファ等)の棚卸し
3. PSRAM アクセスレイテンシの簡易ベンチ: internal RAM と PSRAM 上の
   配列に対する 16B 単位のランダム読み書き(キュー操作を模す)の
   所要時間比較。可能なら「mp3 再生中(= PSRAM/フラッシュアクセス競合下)」
   でも計測する
4. 上記から、L0 キューを internal に置く場合の現実的な最大深さと、
   PSRAM に置く場合のレイテンシ影響の見積もり

### P10-5: UART TX リアルタイムバイト割り込み挿入の PoC

**目的**: 設計判断 5(リアルタイムバイトのメッセージ途中割り込み)が
ESP32 の UART ドライバ構成で実装可能か、受信側が正しく処理するかを確認する。

**方法**: `PHASE10_INTERLEAVE_TEST` ガード内で、(1) Note On/Off の 3 バイト
メッセージを高頻度(例: 10ms 間隔)で送出し続けながら、(2) 24ppqn 相当の
タイミングで 0xF8 を**メッセージ境界を待たずに**挿入する試験コードを実装。
`uart_write_bytes` の呼び出し単位でどこまで割り込めるか(ドライバの TX
リングバッファ経由で足りるか、TX FIFO 直叩きが要るか)を確認する。

**確認内容**:
1. ループバック受信で、(a) 全 Note On/Off がバイト欠落・化けなく届く
   (0xF8 を取り除いた列が送信列と一致する)、(b) 0xF8 の間隔統計が
   ノート送出の有無で悪化しない(E1 統計で比較)
2. SL MK3 実機での確認(ユーザーに接続・目視確認を依頼): ノートを
   受けながらクロック検知テンポが安定しているか。**これはユーザーの
   物理操作が必要なため、手順を提示して依頼し、完了の返答を待つこと**

1. **`docs/architecture.md` の全面改訂案**: 層構成(L0〜L3)、Clock Authority
   (レートマスターの決定と根拠 = P10-1/P10-2 の実測値)、tick 座標系
   (PPQN 960、u32)、MIDI クロックのグリッド生成、ポート抽象、

   構成に合わせる): 候補語彙は以下。各 API のシグネチャ・ABI レイアウト
   (アラインメント・エンディアン明示)・エラーコード・既存 API
   (`hostapi_midi_send`/`hostapi_midi_recv`/`hostapi_click_schedule`)との
   関係(残す/置換する/非推奨化する)を明記する。
   - `transport_{start,stop,continue,locate,get_position}`
   - `tempomap_{set_tempo,set_meter,set_loop}`(at_tick 指定)
   - `seq_{write,flush_after,filled_until}`
   - `time_us_to_tick`(録音打刻の変換用)
3. **各アプリ要件との突き合わせ表**: 高精度メトロノーム / 楽曲メトロノーム
   (セクション・途中テンポ変更・小節毎 PC)/ SMF インポート / 2trk
   シーケンサー+録音 / ドラムマシン(内蔵音源 port)のそれぞれが、
   上記 API 語彙だけで実現できることの確認(不足があれば語彙の追加提案)
4. **数値の根拠表**: 設計書中のすべての定数(PPQN、キュー深さ、horizon、
   バッファサイズ)に P10-1〜5 の実測値または計算根拠を紐づける

設計書のレビュー観点として、**「この API 語彙は要件 1〜5 を通しても増えない」
が層の切り方の検証である**ことを冒頭に明記すること。
