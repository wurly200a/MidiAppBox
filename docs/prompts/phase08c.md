# Phase 08c: MIDI IN ハードウェア検証(受信バイトダンプ)

## 目的

TLP2361 によるフォトカプラ受信回路の実機動作確認。
UART1 に RX を追加し、受信した生バイトを 16 進でログ出力するところまでを対象とする。

**MIDI メッセージのパースは行わない。** ランニングステータス解釈、SysEx 組み立て、
イベント構造体への変換などは本フェーズのスコープ外とする。

## スコープ外(明示)

- Host API / ABI の変更(WASM 側に受信 API を追加しない)
- MIDI パーサの実装
- `scripts/` および `.claude/settings.local.json` の変更(本プロンプトは routine 扱い、read-only)
- LVGL / UI への受信状態表示

## ハードウェア構成

| 項目 | 内容 |
| --- | --- |
| RX ピン | **GPIO15** |
| TX ピン | GPIO18(Phase 08a で実装済み、変更しない) |
| UART | UART1、31250 bps、8N1 |
| 受信回路 | DIN5 → 220Ω → TLP2361(1N4148 逆並列)→ VO を GPIO15 へ直結 |

### 極性に関する必須確認事項

TLP2361 はトーテムポール出力かつ反転型で、MIDI のカレントループ論理(アイドル = 無電流 = 出力 H)が
そのまま UART の論理レベルに一致する。したがって **RXD 側の反転は不要**。

`uart_set_line_inverse` に渡すマスクが `UART_SIGNAL_TXD_INV` のみであることを
コード上で確認し、`UART_SIGNAL_RXD_INV` を追加しないこと。
該当箇所には理由をコメントとして残す。

## 実装内容

1. UART1 の設定に GPIO15 を RX として追加(TX 側の設定は変更しない)
2. `uart_driver_install` の RX リングバッファサイズを設定(SysEx を考慮し 1024 バイト以上)
3. 受信タスクを追加し、`uart_read_bytes` で読んだバイトをそのまま 16 進でログ出力
   - 出力形式は `MIDI RX: F8` のように 1 行 1 バイト、もしくは短時間分をまとめた 1 行
   - タイムスタンプ(ms)を併記すると Clock の間隔確認に使える
4. オーバーラン / フレーミングエラーの発生を UART イベントから検知してログに出す

## 検証手順

以下の順序で行う。ループバックを最初に行わないこと
(TX/RX 双方の極性設定が同時に誤っていた場合、ループバックでは誤りが相殺されて通ってしまうため)。

### Step 1: 外部機器 → 自機 MIDI IN(基準となる検証)

UM-ONE 経由で PC から送信し、自機で受信する。

- Note On / Note Off
- ランニングステータス(同一ステータスで連続するノート)
- アクティブセンシング(0xFE)
- SysEx(リングバッファのオーバーラン確認用に長めのもの)

期待値: 送信したバイト列とログのバイト列が完全一致すること。

### Step 2: 自機 MIDI OUT → 外部機器

Phase 08a で検証済みのため、疎通確認のみ。

### Step 3: ループバック(自機 OUT → 自機 IN)

Step 1 が通ってから実施する。ここでの目的は疎通確認ではなく、
**3.3V 送信 × TLP2361 という最悪ケースのループ電流の評価**。

- バイト落ち、化けが発生しないか
- 不安定な場合は IN 側直列抵抗を 220Ω → 100Ω に変更して再評価
  (5V 送信機からでも LED 電流は約 10mA で絶対最大定格内)

### Step 4: MIDI Clock 連続受信(Phase 08b 実装済みの場合のみ)

24 ppqn の Clock(0xF8)を連続受信し、バイト落ちがないこと、
受信間隔がテンポから計算される値と一致することを確認する。

## 実行環境に関する指示

**実機ビルド、Linux ホスト用ビルド、flash、monitor、カメラ撮影など、
シェルで実行するものはすべて herdr の pane を作成して実行すること。**
直接実行は行わない。

- pane 構成、コマンド、タイムアウト値は `docs/workflow.md` に従う
- pane 操作は `scripts/hpane.sh` を使用する
- 完了待ちは sentinel token で行い、ログテキストのマッチングは使わない

## 完了条件

- Step 1 で送信バイト列と受信ログが完全一致
- Step 3 でループバックが安定動作(または抵抗値変更後に安定動作)
- 最終的な IN 側直列抵抗値と、その判断根拠を `docs/dev-log.md` に記録
- 極性設定(TXD のみ反転)の確認結果を `docs/dev-log.md` に記録
