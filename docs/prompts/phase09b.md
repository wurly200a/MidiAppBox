# Phase 09b: ループバック診断アプリ(MIDI Clock 実測テンポ表示)

## 目的

Phase 09a の `hostapi_midi_recv` を使う最初の WASM アプリを作成する。
自機の MIDI OUT(24ppqn Clock)を自機の MIDI IN で受信し、実測テンポと
クロック間隔の統計をリアルタイム表示する。

このアプリは三役を兼ねる:

1. **配線チェック**: 受信生バイトの表示による OUT/IN 回路の疎通確認
2. **受信 API の実証**: 「アプリが API を駆動する」原則の最初の実例
3. **外部シンク問題の診断**: 120bpm 送信に対し Novation SL MK3 の検知テンポが
   115〜119bpm で常にばらつく事象の定量化

## 前提

- Phase 09a(`hostapi_midi_recv`)が完了していること
- ハードは Phase 08c で検証済みのループバック構成(OUT → IN 直結)

## 診断の設計方針(重要)

SL MK3 の検知テンポは **120 を中心に上下せず、常に下側(115〜119)に振れている**。
対称なジッタだけではこの片寄りは説明できない。仮説は三つあり、アプリは以下の指標で
これらを切り分けられること:

| 仮説 | 切り分け指標 |
| --- | --- |
| (a) クロック間隔の平均が公称 20,833µs より系統的に長い(タイマー周期の丸め等) | **平均間隔 vs 公称値**の偏差表示 |
| (b) クロックの取りこぼし(送信抜け or 受信抜け) | 一定時間内の**受信クロック数** vs 期待数 |
| (c) ジッタ + SL MK3 側の推定窓の癖 | 間隔の **min / max / σ** |

したがって「テンポ表示」だけでなく、平均間隔の公称値からの偏差(µs 単位)と
受信クロック数のカウントを一次情報として表示する。

## アプリ仕様

言語: Rust(`no_std`、`wasm32` ターゲット)。パースはすべてアプリ内で行う。

### 表示(段階実装)

**Stage 1 — 配線チェック**
- 受信した直近バイトの 16 進表示(最新 8〜16 バイト程度のスクロール)
- 累積受信バイト数

**Stage 2 — テンポ表示**
- Clock(0xF8)検出、直近 24 クロック(= 1 拍)の移動平均からテンポ算出
- 表示: 実測 BPM(小数 1〜2 桁)

**Stage 3 — 診断統計**
- クロック間隔の min / max / σ(µs)
- 平均間隔と公称間隔(120bpm なら 20,833µs)との偏差
- 起動からの受信クロック数と、経過時間から計算される期待クロック数の差

Stage 1 を動かしてから 2、3 を積み増す。各 Stage 完了時点でコミットする。

### 実装上の注意

- タイムスタンプは `hostapi_midi_recv` のレコード値のみを使用する。
  `app_tick` の呼び出しタイミングを時刻として使わないこと(約 5ms ジッタがあるため)
- Start(0xFA)/ Stop(0xFC)は既存 API で送信できるため、アプリ内の操作
  (ボタンまたは自動)で Clock 送信の開始 / 停止を制御する
- ランニングステータスは Clock(システムリアルタイム)には無関係だが、
  Stage 1 の生バイト表示では他メッセージ混在も想定してそのまま表示する
- σ の計算は整数演算で可能な範囲の簡易実装でよい(Welford 法など)。
  浮動小数点を使う場合は wasm32 での挙動を確認する

## 測定手順

1. ループバック構成で 120bpm の Clock を送信し、Stage 3 の統計を記録する
2. 平均間隔の偏差、クロック数の過不足、σ を `docs/dev-log.md` に記録する
3. 結果から仮説 (a)(b)(c) のどれが有力かを整理する。送信側(クリックスケジューラ)の
   修正が必要と判断される場合、その修正は本フェーズに含めず、次フェーズの
   調査対象として dev-log に提案を書く

## スコープ外

- Host API / ABI の変更(09a で確定したものを使う。不足が判明した場合は実装せず、
  調査報告として提案を出す)
- 送信側クリックスケジューラの修正
- SL MK3 実機での再測定(ループバック解析の結果が出てから別途)

## 実行環境に関する指示

**実機ビルド、Linux ホスト用ビルド、flash、monitor、カメラ撮影など、シェルで実行する
ものはすべて herdr の pane を作成して実行すること。** 直接実行は行わない。
pane 構成、コマンド、タイムアウト値は `docs/workflow.md` に従い、pane 操作は
`scripts/hpane.sh` を使用する。

## 完了条件

- Stage 1〜3 が実機で動作し、各 Stage でコミットされている
- 同一 `.wasm` が Linux ホストでもエラーなく起動する(09a がスタブの場合、
  受信 0 件時の表示が破綻しないこと)
- 120bpm ループバックの測定結果(平均偏差、クロック数差、min/max/σ)が
  `docs/dev-log.md` に記録され、仮説の切り分け結果が整理されている
