# Phase 09c: MIDI Clock 送信タイミングの再測定と欠落要因の特定

## 目的

現アーキテクチャ(ホストは音楽時間軸を持たず、WASM アプリからの予約 API 通知で
24ppqn クロックを駆動する構成)における MIDI Clock 送信の**タイミング品質を、
再現可能な手順で定量化**し、公称テンポより低く検知される現象の要因を特定する。

本フェーズは**計測と要因特定のみ**を行う。送信側の修正は行わない(後続の
アーキテクチャ刷新フェーズの入力とするため)。

## 前提と、Phase 09b の扱い(重要)

**Phase 09b(`docs/results/phase09b.md`)の測定結果と結論は、本フェーズでは
一切の前提として使わないこと。** 09b の測定は途中で発見された実機配線の
接触不良の影響が混入しており、本文と追記で結論が二転している。数値も
カメラ撮影画像からの目視読み取りを含み信頼できない。

09b から引き継いでよいのは以下のみ:

- `wasm-apps/midi_loopback/` の実装が存在すること(本フェーズで改修して使う)
- `hostapi_midi_recv`(Phase 09a)の API 仕様
- トラブル対処の教訓(`docs/results/phase09b.md` の「トラブルと教訓」節、
  および `docs/lessons.md`)

09b の測定値・仮説の評価・結論は参照しない。本フェーズはゼロベースで測定する。

## 現在確認されている現象(ユーザー報告)

配線修正後の現在、SL MK3 に 120bpm の Clock を送ると、**基本的に 115bpm 付近、
たまに 119bpm** という値を規則正しく繰り返し検知する。単発の異常ではなく
再現性のある定常的な挙動である。

## 有力仮説(コードリーディングによる。検証対象であって前提ではない)

`src/components/midi/midi.cpp` の `Midi_NotifyBeatFired()` は、拍ごとに
`esp_timer_stop()` → `esp_timer_start_periodic()` でクロックタイマの位相を
リセットしている。120bpm では:

- `interval_us = period_ms * 1000 / kClockPpqn = 500 * 1000 / 24 = 20833`
  (整数除算。真値 20833.33 の切り捨て)
- 再アーム基準時刻から 24 発目の発火は `24 * 20833 = 499,992µs`
- 次拍の再アームは公称 500,000µs 後。**マージンはわずか 8µs**

したがって、拍境界の再アームがクロック位相に対してわずかでも早く来ると
24 発目が切り落とされ、その拍のクロックは 23 発になる。クリックスケジューラ側の
発火タイミングには ms オーダーのジッタがあるため、これは確率的に発生しうる。

この仮説が正しい場合の予測値(**測定前に記録しておき、実測と突き合わせること**):

| 予測項目 | 予測値 |
| --- | --- |
| 欠落発生時のクロック間隔(外れ値) | 約 41,674µs(= 公称の約 2 倍) |
| 欠落を 1 回含む 24 クロック窓の見かけ BPM | 約 115.2 |
| 欠落を含まない窓の見かけ BPM | 約 120.0 |
| 1 拍あたりのクロック数 | 24 または 23 の二値をとる |
| 定常区間(欠落を除く)のクロック間隔 | 20833µs 付近、σ は小さい |

**この仮説に沿う証拠だけを集めないこと。** E1 は仮説に依存しない生データの
取得であり、必ず E1 → E2 → E3 の順で実施する。E1 の時点で上記予測と食い違う
結果(例: 1 拍あたりのクロック数が常に 24、外れ値が 41.7ms 以外の値に集中する、
定常区間の平均が 20833µs から系統的にずれている)が出た場合は、仮説を捨てて
その事実を報告し、E2 以降の設計をユーザーと相談すること。

## 測定設計

### 共通条件(全実験で固定・記録する)

- ループバック構成(自機 MIDI OUT → 自機 MIDI IN 直結)
- テンポ 120bpm 固定、4/4
- START 後は**実機に一切触れない**(タッチ由来のノイズを排除)
- 測定時間は 1 回あたり 120 秒(公称クロック数 5760 発)
- 同一条件で **3 回**繰り返し、再現性を確認する
- 測定開始・終了時刻、ビルドのコミットハッシュを記録

### E1: ベースライン測定(仮説非依存の生データ)

`wasm-apps/midi_loopback/` を改修し、以下を取得する。既存の Stage 3 統計
(セッション全体の min/max/σ)は外れ値に平均が引っ張られて定常時の挙動を
表さないため、**分布を見る指標に置き換える**。

取得項目:

1. **クロック間隔のヒストグラム**
   バケット例: `<20000`, `20000-20499`, `20500-20999`, `21000-21499`,
   `21500-29999`, `30000-39999`, `40000-44999`, `45000+` の 8 バケット程度。
   バケット境界は上記予測値(20833 と 41674)を分離できるように設計すること。
   各バケットの件数を表示する。
2. **ロバスト統計**: 中央値、および外れ値(中央値の 1.5 倍を超える間隔)を
   除外した平均・σ・min/max。外れ値の件数も別途表示。
3. **外れ値の実測値そのもの**: 直近 8 件の外れ値の µs 値を保持して表示する
   (41674 付近に集中するかを直接確認するため)。
4. **総受信クロック数と、初回受信〜最終受信のタイムスタンプ差から計算した
   期待クロック数**(既存 Stage 3 と同じ算出方法)。
5. **見かけ BPM の分布**: 24 クロック移動平均 BPM を、`114-116`, `116-118`,
   `118-119.5`, `119.5-120.5`, その他 のバケットで計数する。
   115 付近と 120 付近の二峰性が出るかを確認する。

実装上の注意(09b から継続):

- タイムスタンプは `hostapi_midi_recv` のレコード値のみを使用する。
  `app_tick` の呼び出しタイミングを時刻として使わない。
- 浮動小数点を使わず整数演算で実装する(既存 Stage 3 と同方針)。
- 表示は実機画面に収まる範囲で。全項目が一画面に入らない場合は、
  ヒストグラムと BPM 分布を主、ロバスト統計を副として、
  ボタンで表示を切り替えるか二画面に分ける。
- **測定値の読み取りはカメラ静止画に頼らないこと。** 判読ミスの実績がある。
  STOP 時に全統計値をシリアルログへ 1 行ずつ出力し、`captures/phase09c/` 配下の
  モニタログから数値を取得する。画面表示はユーザーが目視で確認するための
  ものと位置づける。

### E2: 送信側の直接観測(ホスト側計測コードの一時追加)

E1 は受信側から見た結果であり、欠落が送信側で起きているのか受信側で
起きているのかを区別できない。ホスト側に**検証専用の計測コード**を追加し、
送信の実態を直接記録する。

`#ifdef PHASE9C_TXLOG_TEST` ガード内に実装し、検証完了後に削除すること
(`docs/workflow.md` および CLAUDE.md のテストコード方針に従う)。

計測項目:

1. `clock_timer_cb()` で `uart_write_bytes` を呼んだ**直前**の
   `esp_timer_get_time()` と、送信した通算クロック数。
2. `Midi_NotifyBeatFired()` が呼ばれた時刻と、そこで計算された
   `interval_us`、および `esp_timer_stop`/`esp_timer_start_periodic` の戻り値。
3. **直近の再アームから、そのアーム区間で実際に何発のクロックを送出したか**
   (再アーム時に前区間のカウントを確定してログ出力する)。これが本フェーズの
   最重要指標である。24 と 23 が混在するか、常に 24 か、で仮説の可否が決まる。

ログ出力はクロック 1 発ごとに `ESP_LOGI` を出すと 48 行/秒でモニタが溢れ、
かつログ出力自体が送信タイミングに影響する。**リングバッファに数値だけを溜め、
STOP 時にまとめてダンプする**方式にすること。溜める件数は 120 秒の測定を
カバーできない場合、直近 N 拍分に限定してよい(その旨を記録する)。

E1 と E2 は**同一の測定セッションで同時に取得する**こと(送信側カウントと
受信側カウントを同じ区間で突き合わせるため)。

### E3: 対照実験(位相リセットの無効化)

E1/E2 で仮説が支持された場合にのみ実施する。支持されなかった場合は実施せず、
E1/E2 の結果を報告して停止すること。

`#ifdef PHASE9C_FREERUN_TEST` ガード内で、`Midi_NotifyBeatFired()` の
再アーム処理を「**すでにタイマーが走っている場合は再アームしない**
(周期が変わったときだけ再アームする)」に変更した変種ビルドを作り、
同一条件で E1 と同じ測定を行う。

期待される結果(仮説が正しい場合): 41.7ms 付近の外れ値が消え、
1 拍あたりのクロック数が常に 24 になり、見かけ BPM の 115 付近のピークが
消えて 120 付近に集約される。

**この変種は恒久的な修正ではない**(テンポ変更時の位相制御・小節同期の
設計は後続のアーキテクチャ刷新で扱う)。検証後、E3 のコードは削除し、
`main` の挙動は E1/E2 時点のまま変更しないこと。

### E4: SL MK3 実機での確認(ユーザー操作、任意)

E3 で改善が確認できた場合、ユーザーに SL MK3 への接続と検知テンポの
読み取りを依頼し、115〜119bpm という現象が変化するかを確認する。
これはユーザーの物理操作が必要なため、E3 完了後に手順を提示して依頼すること。

## スコープ外

- Host API / ABI の変更(必要と判明した場合は実装せず、調査報告として提案を出す)
- 送信側クリックスケジューラの恒久的な修正(E3 は検証用の一時変種のみ)
- ホスト側への音楽時間軸(テンポマップ・小節管理)導入(後続フェーズ)
- 120bpm 以外のテンポでの測定(`period_ms` の整数丸めに起因する別の系統誤差が
  予想されるが、本フェーズでは扱わない。ただし E1 の実装が他テンポでも
  そのまま使えるようにはしておくこと)
- Song Position Pointer 等の高度な MIDI 同期

## 実行環境に関する指示

**実機ビルド、Linux ホスト用ビルド、flash、monitor、カメラ撮影など、シェルで
実行するものはすべて herdr の pane を作成して実行すること。** 直接実行は行わない。
pane 構成、コマンド、タイムアウト値は `docs/workflow.md` に従い、pane 操作は
`scripts/hpane.sh` を使用する。セッション開始時に `docs/workflow.md` を通読すること。

flash 前に `esp32-monitor` の docker コンテナがシリアルポートを保持していないか
`docker ps` で確認する(既知の教訓)。
