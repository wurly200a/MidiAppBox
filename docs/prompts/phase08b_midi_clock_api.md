# Phase 8b: MIDI Clock 出力 Host API 追加 + メトロノームアプリへの実装

## 前提

Phase 8a で MIDI OUT 回路（GPIO18 = UART1 TX, 31250bps 8N1,
`uart_set_line_inverse` 済み）の疎通確認は完了済み。本Phaseはその続き。

Phase 7C で「2ms tick を app_tick 側で回して精密スケジューリングの代替に
する」方式は、`app_tick` の実行時間が実測 ~5ms（LVGL ロック競合 +
i2s_write）に達するため棄却済み。この事実は本Phaseの設計方針を
決める前提として引き続き有効。

## 設計方針（確定事項として実装すること）

- **24 ppqn の MIDI Clock (0xF8) は native host 側の既存クリックスケジューラを
  拡張して生成する。** WASMアプリの `app_tick` には一切タイミングを
  依存させない。テンポ情報はすでにクリック生成のために host 側で
  保持されているはずなので、新規のテンポ伝達経路は原則追加しない。
- **WASMアプリが呼ぶ Host API は Start (0xFA) / Stop (0xFC) /
  Continue (0xFB) のようなワンショットのシステムリアルタイムメッセージの
  送信のみ。** これはユーザー操作の瞬間に1回送るだけなので `app_tick`
  経由で問題ない。
- Host API 自体は汎用的な MIDI バイト送信関数
  （例: `hostapi_midi_send(const uint8_t* bytes, size_t len)`）1つに
  留め、24ppqn クロックの生成ロジックは host 内部に隠蔽する。
  appは「クロックを出せ」という抽象命令ではなく「このバイト列を今すぐ
  送れ」という薄いAPIだけを使う（App drives API 原則）。

## 進め方（承認ゲート）

Host API/ABI の変更を含むため、以下の順序を厳守すること。
一気に実装まで進めないこと。

### ステップ1: 投資方針レポート（コードを書く前に提示）

以下を含む短い報告を出すこと：

1. **Host API の具体的な関数シグネチャ**（引数・戻り値・エラー処理）
2. **既存クリックスケジューラのどこに 24ppqn クロック生成を差し込むか**
   （現在テンポと次回発音時刻をどう保持しているか、その構造を
   変更せずに拡張できるか、変更が必要ならどこを触るか）
3. **Linux/SDL ホストと実機ホストの両方でのMIDI送信経路の違い**
   （実機は UART1 実送信、Linux側はダミー実装 or 標準入出力への
   ログ出力等になるはずだが、どちらで実装するか）
4. **WASMアプリ側に追加する内容**（Start/Stop/ContinueをどのUI操作に
   紐づけるか。既存のメトロノーム開始/停止ボタンに相乗りさせるのが
   自然だが、それでよいか）
5. **既存のクリック音生成タイミングとMIDI Clock送信タイミングの関係**
   （4分音符ごとのクリックと24ppqnクロックは別々にスケジュールする
   必要があるため、二重にタイマーを持つのか、どちらかから導出するのか）

### ステップ2: 承認

上記レポートに対して私が承認してから実装に進むこと。
Host API/ABIのシグネチャは承認後に変更しないこと
（変更が必要になった場合は再度レポート→承認）。

### ステップ3: 実装

承認後、Host API 追加 → native host 実装（Linux/SDL・実機の両方）→
WASMアプリ実装、まで一気に進めてよい。ビルド・書き込み・モニタは
必ず `herdr` の pane 経由で実行すること（直接実行禁止）。

## テスト内容

Phase 8a と同じ UM-ONE 経由の確認に加えて、以下を確認する：

- メトロノーム開始 → Start (0xFA) が1回送信される
- 開始後、テンポに応じた間隔で 0xF8 が24回/拍のペースで送信され続ける
- メトロノーム停止 → Stop (0xFC) が1回送信される
- テンポ変更時、0xF8 の送信間隔が追従して変わる
- クリック音のタイミングと 0xF8 送信のタイミングがずれない
  （目視では確認しづらいので、外部シーケンサ/DAW側でMIDI Clockを
  受けてテンポ追従させ、クリック音と同期しているか耳で確認する）

## 成功条件

- UM-ONE を介して外部のDAW/シンセがこのMIDI Clockに同期して動作する
  （最も分かりやすい確認は、DAW側のトランスポートをMIDI Clock同期
  モードにして、開始・停止・テンポ変更が本デバイス側の操作に追従する
  ことを確認する）
- `app_tick` の実行時間が Phase 7C 時点の値から悪化していない
  （新規のMIDI送信処理が app_tick 側の負荷にならないことの確認）

## スコープ外（このPhaseではやらないこと）

- Song Position Pointer 等の高度なMIDI同期メッセージ
- MIDI IN（TLP2361）側の実装・受信によるテンポ追従
- 複数出力先の同時サポート

## 完了後

動作確認が取れたら、Zenn記事シリーズの新規記事（またはPhase 8a/8bを
まとめた1記事）の材料として、fast-tick棄却の経緯（Phase 7C由来）と
24ppqn生成をhost側に隠した設計判断を明記しておくと、既存記事群との
一貫性が出る。
