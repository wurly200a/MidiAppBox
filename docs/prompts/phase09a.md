# Phase 09a: Host API `hostapi_midi_recv` の追加(タイムスタンプ付き MIDI 受信)

## 目的

WASM アプリが MIDI 受信バイトを**ホスト側で付与された受信時刻タイムスタンプ付き**で
取得できる Host API を追加する。

設計原則の再確認: タイミングクリティカルな処理(受信時刻の記録)はネイティブホスト側、
ロジック(パース、テンポ計算)は WASM アプリ側。タイムスタンプをホストの UART イベント
タスクで受信直後に打つことにより、`app_tick` の約 5ms ジッタがアプリのタイミング計測に
影響しない構造とする。

## ゲート(必須)

本フェーズは Host API / ABI の変更を伴う。**調査報告 → 明示的承認 → 実装**の順を厳守する。
調査報告で提示すべき項目は「調査報告に含める事項」を参照。承認前にコードを変更しないこと。

## API 仕様(たたき台 — 調査報告で確定させる)

```
hostapi_midi_recv(buf_ptr: u32, buf_len: u32) -> i32
  戻り値: 書き込んだレコード数(0 以上)、エラー時は負値
  レコード: { timestamp_us: u64(LE), byte: u8 } の繰り返し
```

- 呼び出しごとに、リングバッファに溜まっているレコードを buf に収まる分だけ吸い出す
- パース(ランニングステータス、Clock 検出など)はホスト側では一切行わない。
  生バイト + タイムスタンプのみを渡す
- タイムスタンプは `esp_timer_get_time()`(µs、単調増加)。既存の Clock 送信側と
  同一時間軸であることを確認する

## 調査報告に含める事項

1. **レコードの ABI レイアウト**: パディング / アラインメントを明示した確定バイトレイアウト
   (例: 9 バイト packed か、16 バイトアラインか)。エンディアンは LE 固定。
   `docs/` 配下の ABI ドキュメントに追記する箇所も示す
2. **ホスト側バッファ構成**: UART イベントタスク → リングバッファ → API 読み出しの
   排他方式(ロックフリー / 短ロック)。バッファ満杯時の方針(古いレコードを捨てる /
   新規を捨てる)とオーバーフロー検知の伝え方
3. **タイムスタンプ分解能**: 現状の UART RX FIFO 閾値・timeout 設定で、1 イベントに
   複数バイトがまとめて届く条件と、その場合のタイムスタンプの意味(イベント時刻で
   代表される)。ジッタ計測用途に対して閾値 / timeout を変更すべきかの判断
4. **Linux ホスト(SDL2)側の実装方針**: ALSA rawmidi 経由で UM-ONE から実受信するか、
   本フェーズではレコード 0 件を返すスタブとするか。同一 `.wasm` が両ホストで動く
   原則を壊さない範囲で、最小実装の提案を優先する
5. **既存 `hostapi_midi_send` との対称性**: 命名、エラーコード体系の整合

## スコープ外

- MIDI パーサ(アプリ側 = Phase 09b の責務)
- アプリ実装(Phase 09b)
- Clock 送信側の変更
- UI / LVGL への変更

## テストコード

- API 単体の疎通確認用テストコードは `#ifdef PHASE9A_RECV_TEST` ガード内に置き、
  検証完了後に削除する
- 確認内容: UM-ONE から送信 → アプリ側バッファにレコードが正しいレイアウトで
  積まれること、タイムスタンプが単調増加であること

## 実行環境に関する指示

**実機ビルド、Linux ホスト用ビルド、flash、monitor、カメラ撮影など、シェルで実行する
ものはすべて herdr の pane を作成して実行すること。** 直接実行は行わない。
pane 構成、コマンド、タイムアウト値は `docs/workflow.md` に従い、pane 操作は
`scripts/hpane.sh` を使用する。

- 調査報告が承認され、承認済みレイアウトどおりに実装されている

- Linux ホストで同一 `.wasm` がエラーなく動作する(スタブ実装の場合は 0 件返却)
- ABI ドキュメントが更新されている
