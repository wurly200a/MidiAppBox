# Phase 9b: ループバック診断アプリ(MIDI Clock 実測テンポ表示) (2026-08-17) — 完了

対応: `docs/prompts/phase09b.md`。Phase 9a の `hostapi_midi_recv` を使う
最初の WASM アプリ `wasm-apps/midi_loopback/` を Stage 1〜3 の段階実装で
作成した(各 Stage で実機検証・コミット)。Host API/ABI の変更は行っていない。

**Stage 1(配線チェック)**: START/STOP ボタンで自機 MIDI OUT の Start
(0xFA)/Stop(0xFC)を送信し(BPM 120 固定、`hostapi_click_schedule` の
毎 tick 再予約で host 内部の 24ppqn クロック生成を駆動する、既存
メトロノームと同じ方式)、`hostapi_midi_recv` で自機 MIDI IN の受信を
直近 16 バイトの 16進表示 + 累積バイト数で可視化。実機でループバック
配線(Phase 8c で検証済みの OUT→IN 直結)から Clock(`F8`)の受信を確認
(RX bytes: 384、全バイト `F8`)。

**Stage 2(テンポ表示)**: Clock(0xF8)を検出し、直近 24 クロック(=1拍)の
リングバッファ移動平均から実測 BPM を x100 固定小数点で算出・表示
(浮動小数点は使わず整数演算のみ)。タイムスタンプは `hostapi_midi_recv`
のレコード値(host 打刻の µs)のみを使用し、`app_tick` 呼び出しタイミング
(約 5ms ジッタ)は使わない(指示書どおり)。実機で BPM 119.97 を確認
(公称 120bpm に対し偏差 0.03、短時間・妨害なしの区間では良好な一致)。

**Stage 3(診断統計)**: セッション全体(START からの)のクロック間隔
min/max・標準偏差 σ・公称間隔(20833µs、120bpm・24ppqn)からの平均偏差・
受信クロック数 vs 期待クロック数(初回受信〜直近受信のタイムスタンプ差分
から算出、こちらも `app_tick` タイミングは使わない)を表示。平均・分散は
整数 Welford 法で逐次計算し、生の sum/sum^2 を保持しない(長時間実行での
桁あふれを回避、指示書の「整数演算で可能な範囲の簡易実装」に沿う)。
σ は自作の整数平方根(Newton 法)。

## 測定結果と仮説の切り分け

複数回のループバック実測(実機、120bpm 送信)で得られた結果:

| 測定 | 条件 | RX bytes | BPM(直近24clk移動平均) | avg dev | min/max | σ | clocks / exp |
|---|---|---|---|---|---|---|---|
| Stage 2 短時間試験 | 数秒、画面操作なし | 384 | 119.97 | (Stage3未実装) | - | - | - |
| Stage 3 試験1 | 約44分放置(未制御) | 5742 | 118.23 | +3233us n=5751 | 20807/**5157892**us | 68309us | 5779 / 6186 |
| Stage 3 試験2(手が画面付近) | 約2分、STOP付近に手 | - | 71.99 | +1830us n=8705 | 20534/**233237**us | 4753us | 8704 / 8940 |
| Stage 3 試験3(手を完全に離す) | 90秒 START→STOP、無操作 | 7715 | 119.97 | +55334us n=7716 | 20529/**7204977**us | 180997us | 7772 / 26743 |

(桁数の一部はカメラ撮影画像からの目視読み取りのため ±1桁程度の誤差を含む
可能性がある。傾向・オーダーは全試験で一貫している。)

**仮説 (a)(平均間隔の系統的なずれ)への評価**: 妨害のない短時間区間
(Stage 2 短時間試験)では BPM 119.97(公称 120 との差はわずか 0.03)と
極めて良好な一致を示した。これは「クロック間隔の平均が系統的に公称値より
長い」という仮説を支持しない。Stage 3 の avg dev が数千〜数万 µs という
大きな正の値になっているのは、後述する少数の巨大な外れ値(min/max の
max 列)に平均が強く引っ張られているためであり、系統的なタイマー周期の
丸め等が主因とは考えにくい。

**仮説 (b)(クロックの取りこぼし)への評価**: 3 回の Stage 3 試験すべてで
「受信クロック数(clocks)」が「期待クロック数(exp)」を大幅に下回った
(試験1: 93%、試験3 に至っては 29% しか受信できていない)。かつ
min/max の max が公称間隔(20833µs)の数十〜数百倍という極端な外れ値を
毎回含んでいた。試験3 は START 後に実機へ一切触れず 90 秒放置した条件
でも同様の傾向(clocks 7772 に対し exp 26743)が再現しており、**画面操作
(誤タップ)の影響だけでは説明できない、何らかの要因でクロックが長時間
途絶する現象がある**ことを示している。3 仮説のうち最も強く支持される。

**仮説 (c)(ジッタ + SL MK3 側の癖)への評価**: 外れ値を除いた通常区間の
min はどの試験も 20500〜20900µs 台で公称値(20833µs)に極めて近く、
定常時のジッタ自体は小さい(1 拍= 24 クロックの移動平均が短時間試験で
0.03bpm の精度で一致していることとも整合する)。σ が数万〜十数万 µs
まで膨れ上がっているのはほぼ全て上記の巨大外れ値によるもので、
定常時のジッタそのものを表す指標にはなっていない(セッション全体の
単純な population 統計の限界。外れ値を除いた区間限定の統計は本フェーズの
スコープ外)。

**結論**: 3仮説のうち (b)(クロックの取りこぼし・長時間の途絶)が最も
有力。定常時(外れ値を除く)は 20500〜20900µs 台のクロック間隔で
安定しており、(a) 系統的なずれの証拠は見られない。(c) は本データからは
判断材料が乏しい(SL MK3 実機での再測定はスコープ外)。

**次フェーズへの提案(本フェーズのスコープ外、送信側クリックスケジューラの
修正は実施していない)**:
1. 巨大外れ値(数百ms〜数秒の Clock 途絶)の発生条件の特定。本フェーズの
   試験3(無操作 90 秒)でも再現しているため、タッチ操作起因だけでなく
   host 側のクロック生成タイマ(Phase 8b の `esp_timer_start_periodic`
   の stop→start 再同期処理、`midi.cpp` の `Midi_NotifyBeatFired`)や
   WASM 側の `hostapi_click_schedule` 毎 tick 再予約の間隔(100ms tick)
   に起因する取りこぼしの可能性を疑い、host 側のログ計測(送信側にも
   Phase 8c 同様のタイムスタンプ付きログを一時的に追加する等)で
   切り分けること。
2. 外れ値を除いた区間限定統計(例: 直近 N 件のみ、または中央値ベースの
   ロバスト統計)を診断アプリに追加すると、定常時のジッタをより正確に
   捉えられる可能性がある。
3. SL MK3 実機での再測定は、上記 1 の host 側要因を切り分けたのちに
   実施する方が診断精度が高い。

## トラブルと教訓

- Linux ホストの `midibox_host` を `| tee <ログ>` でパイプすると標準出力が
  フルバッファリングになり `waitfor` から見えるまで遅延する
  (Phase 9a と同じ現象。`stdbuf -oL -eL` で解消、教訓を再確認)。
- `herdr` の pane の scrollback に古い出力が残っていると、`hpane.sh run`
  の番兵トークン一致が新しい出力ではなく scrollback 中の古い一致文言に
  ヒットしてしまうことがある(`waitfor`/`run` 双方で発生)。`sleep` を
  挟んで `read` で最新状態を明示的に確認する方が確実。
- カメラ静止画がユーザーの手や向きのズレで判読困難になることが複数回
  あった(黒画面・被写体ブレ・指が画面に重なる等)。実機のタッチ操作を
  ユーザーに依頼する運用上、操作直後は手が画面近くに残りやすく、
  静止画のタイミングと干渉しやすい。今回は「操作→完全に手を離す→
  数秒待ってから撮影」の順を徹底することで解消した。
- ESP32 実機ビルド後の `idf.py flash` が「デバイスが busy」で失敗する
  ことがあった。原因は直前の `esp32-monitor` の docker コンテナ
  (`idf.py monitor`)がシリアルポートを保持したままだったこと。
  flash 前に `docker ps` で該当コンテナの有無を確認し、あれば
  `docker kill` してから flash することで解消(Phase 8c の教訓の再確認)。

(`monitor_stage1.log`〜`monitor_stage3.log`)と静止画・録画(`stage1/`〜
`stage3_final/`)。

## Phase 9b 追記: 接触不良修正後の再測定 (2026-08-17)

ユーザーが実機配線の接触不良を発見・修正。同一ファームウェア(再フラッシュ
不要、Stage 3 のビルドをそのまま使用)で 120bpm ループバックを再測定。

**再測定条件**: START 後 90 秒、画面無操作(手を触れない)。

**再測定結果**: RX bytes 8955、BPM(直近24clk移動平均)118.22、
avg dev **+183us** n=8953、min/max 20518/**41972**us、σ 3409us、
clocks 8954 / exp 9081(**98.6%**)。

**前回結果との比較**: avg dev は前回試験(+1830〜+55334us)から
**2桁小さい +183us** に、max の外れ値も前回(23万〜720万µs)から
**41972us(公称値の約2倍、1回分のクロック取りこぼしに相当する規模)**
に大幅改善。clocks/exp も前回の 71〜93% から **98.6%** に改善。
これは、前回観測された大きな外れ値と大幅なクロック取りこぼしの**主因が
配線の接触不良であった**ことを強く示す。

**残る所見(修正後も残る小さな偏差)**: 接触不良修正後も、
(1) 公称間隔 20833µs に対し平均は +183µs(小さいが単純なジッタでは
説明しづらい方向への偏り)、(2) 42ms(公称の約2倍)の外れ値が最低 1件、
(3) clocks/exp が 100% ではなく 98.6%(約1.4%の取りこぼしが残る)
という3点が確認できる。いずれも修正前と比べて小さいオーダーだが、
ゼロではない。これらが (a) 系統的なタイマー丸め、(b) ごく低頻度の
クロック取りこぼし、のどちらに起因するかは本追記時点のデータからは
断定できない(サンプル数を増やした複数回の再測定が必要)。

**結論の更新**: 当初の Phase 9b 本文で「(b) クロックの取りこぼしが
最有力」とした判断は、**大部分が配線の接触不良によるものだった**と
訂正する。接触不良を除去した後も 1.4% 程度の取りこぼしと小さな系統的
偏差が残ることから、(b) の要因が完全にゼロとは言えないが、その規模は
当初観測したものより大幅に小さい。SL MK3 の 115〜119bpm という検知結果
(公称 120bpm に対し 1〜5bpm 低い)を説明できる規模かどうかは、今回の
残存偏差(BPM 118.22、公称より 1.78bpm 低い)が同程度のオーダーであり、
**接触不良のような配線側の要因を洗い出した上で、なお残る若干の低め
バイアスが SL MK3 側の検知結果と同じ方向・同程度のオーダー**である
可能性を示唆する。次フェーズでは、この残存偏差(数百µs〜数%の取りこぼし)
の再現性を複数回の測定で確認することを提案する。
