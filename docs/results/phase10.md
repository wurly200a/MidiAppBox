## P10-1: I2S 再生位置(消費済みサンプル数)の取得可能性 【go/no-go ゲート】(2026-08-30) — **判定: go**

### 方法

`src/components/audio/audio.cpp` に `#ifdef PHASE10_I2SPOS_TEST` ガードで
調査コードを実装(検証完了後に削除済み。削除前の全差分は

- **(b) on_sent コールバック**: `i2s_channel_register_event_callback` で TX の

### (a) 書き込み累計方式の評価

- 累計カウント自体は成立する(run3: metronome 10 秒窓で 221,040B = 20 クリック
  × 11,052B、120bpm と正確に一致)。
- ただし **write が発生している間しかカウントが進まない**(アイドル・クリック間の
  無音区間では DAC はゼロを消費し続けるが、書き込み累計は止まる)。

  min 9µs / max 44.7〜51.6ms。DMA に空きができるまで待つため、MP3 の
  デコードチャンク単位で数十 ms ブロックする)。
- よって (a) 単独ではレートマスターに使えない。**(b) を採用**。

## P10-2: 実効サンプルレートの ppm 計測(2026-08-30) — 完了

### 方法

P10-1 の計測ビルド(実機に焼かれたままのもの)をそのまま使用。コード変更なし。
ボードをリセット後、ランチャー画面のまま完全アイドル(タッチ・アプリ起動・
write 一切なし)で約 7 分間、10 秒毎のダンプ(累計 sent バイトと span_us が
整数で出力される)を収集。同一条件で 2 回(run A/B、各回ともリセットから開始)。

後処理: ダンプ間の差分から `実効fs = Δframes / Δus × 10^6` を全区間と
30 秒窓(3 ダンプ毎の非重複窓)で算出。窓端の打刻ジッタ(±62µs 最悪)は
30 秒窓で ±2ppm 未満、実測 σ0.5µs では ±0.03ppm 程度の量子化誤差に相当。

生データ: `captures/phase10/monitor_p10_2_runA.log` / `monitor_p10_2_runB.log`、
解析スクリプト: `captures/phase10/p10_2_ppm.py`。

### 結果

| 項目 | run A | run B |
|---|---|---|
| 全区間スパン | 430.9 s | 410.8 s |
| 全区間の実効 fs | 44100.0000 Hz | 44100.0000 Hz |
| 公称比 ppm(全区間) | −0.00 | −0.00 |
| 30 秒窓の ppm 変動幅 | 0.03 ppm(n=14、−0.00〜+0.03) | 0.06 ppm(n=13、−0.03〜+0.03) |
| 打刻間隔統計(参考) | n=81,006、σ0.5µs、全数が 5400-5499 バケット | n=79,165、σ0.5µs、全数が 5400-5499 バケット |
| 条件の清浄度 | タッチ 0・アプリ起動 0・WARN/ERROR 0 | 同左 |

### 考察(なぜ厳密に 0 ppm か)

I2S クロック(PLL 160MHz 系)も esp_timer(XTAL 40MHz 系)も**同一の水晶**から
派生しており、かつ ESP32-S3 の I2S 分数分周は 44.1kHz に対して厳密な有理比を
達成できる: MCLK = 160MHz × 441/6250 = 11,289,600 Hz = 256 × 44100(分母
441 は分数分周器の分解能内)。したがって「分数分周の丸め」による系統誤差は
44.1kHz では**原理的にゼロ**であり、実測(±0.03ppm = 測定量子化の範囲)と一致する。
温度による揺らぎも観測されない(両クロックが同一水晶なので相対比からは
水晶自体のドリフトが相殺される。実時間に対する絶対精度は水晶精度
(数十 ppm 級)に依存するが、系内の時刻変換には影響しない)。

### 結論(Clock Authority の対応更新方式)

- **固定比で足りる。逐次推定(PLL/フィードバック)は不要。**
  (sample_count, us) の対応は公称値 44100 の固定換算+起動時のオフセット
  確定のみで、系内誤差は補間誤差(P10-1 実測 最悪 ±62µs)に支配される。
- 注意: これは同一 XTAL 系である ESP32-S3 実機の性質。ブラウザホスト
  (Phase A)等、オーディオクロックとタイマクロックが別系統の環境では
  逐次推定が必要になりうる(設計書で環境差として明記する)。
- 22.05kHz 等へのレート切替時は換算係数の切替が必要(cur_rate 連動)。
  44.1kHz 以外のレートでも同様の厳密比が成るかは未測定(現用途は
  44.1kHz 固定のためスコープ外)。

## P10-3: ワンショット再アーム方式のジッタ実測(2026-08-30) — 完了

### 方法

`src/components/midi/midi.cpp` + `src/components/wasm_runtime/hostapi.cpp` に
`#ifdef PHASE10_ONESHOT_TEST` ガードで実装(検証完了後に削除済み。全差分は
`captures/phase10/p10_3_test_code.patch`)。

- **TX**: esp_timer ワンショット(ESP_TIMER_TASK ディスパッチ)で 20833µs
  間隔の 0xF8 送出連鎖。再アームは**前回の予定時刻 + 20833µs の絶対加算**
  (発火時刻基準ではない。予定が過去になった場合は 1µs 後に発火して
  グリッドに追いつく方式で、その回数を late として計数)。発火偏差
  (発火時刻 − 予定時刻)を逐次統計。
- **RX**: rx_task の打刻点(`hostapi_midi_recv` と同一のタイムスタンプ源)で
  0xF8 受信間隔を 9c E1 と同一バケット・同一除外閾値(31250µs)で逐次統計。
  WASM アプリの有無によらず計測できるため、「ランチャーアイドル」
  「mp3player 再生+タッチ」の両条件を同一計器で計測した。
- ガード内で旧 periodic クロック経路(`Midi_NotifyBeatFired`)を無効化し
  0xF8 源を一本化。rxq 満杯警告はカウンタ化(消費アプリ不在時は満杯が正常)。
- hostapi.cpp に 9c と同方式のセンチネル転送フック(x≥1000 の draw_text を
  シリアルへ)を追加し、midi_loopback の E1 統計とのクロスチェックを実施。
- 統計ダンプタスクは優先度 2(P10-1 の教訓に従い audio_player より低く)。

生データ: `captures/phase10/monitor_p10_3_idle{1,2}.log`(アイドル 130s×2、
各回リセット起点)、`monitor_p10_3_load.log`(loopback E1×2 + mp3+タッチ×2 を

### 結論

- **ワンショット連鎖 + 絶対時刻グリッド方式は成立する。** 最悪負荷
  (mp3 再生 + LVGL + タッチ割り込み)下でも欠落 0・追いつき 0・
  発火偏差 max 104µs。設計候補 2(L0 ディスパッチャのワンショット 1 本
  + tick→host 時刻変換で arm)と矛盾なし。
- 09c で periodic に対して懸念された「再アーム処理分の悪化」は観測されず、
  むしろ毎拍位相リセットの廃止で外れ値が完全に消えた(E3 の対照実験結果とも
  整合)。
- 発火偏差の系統分 (~16-26µs) は定数オフセットであり、必要なら予定時刻を
  その分前倒しして補正できる(設計書に記載)。
- **設計への申し送り**: 受信打刻(rx_task、優先度 5)は高優先度タスクの
  干渉で ±3ms 級の遅延が稀に入る。`time_us_to_tick`(録音打刻)の精度要件を
  詰める際は、送信グリッド精度(~100µs)と受信打刻精度(~ms 級のテール)を
  区別して扱うこと。
- 観測メモ: midi_loopback 終了時に free heap が 220B 減る事象を 1 回観測
  (計測ビルド)。フェーズ完了時の main ビルド回帰確認で再確認する。

## P10-4: メモリ監査(2026-08-30) — 部分完了(PSRAM ベンチのみ未取得)

### 方法

`src/main/app_main.cpp` に `#ifdef PHASE10_MEMAUDIT_TEST` ガードで監査コードを
実装(検証後に削除済み。差分は `captures/phase10/p10_4_test_code.patch`)。
10 秒毎に INTERNAL / SPIRAM のヒープ情報(free / largest / min_free / allocated)を
ダンプし、30 秒毎に 16B 単位のランダム読み書きベンチ(L0 キュー操作を模した
read 16B → write 16B を 8192 回)を実行。静的追加は約 5.5KB(2KB 配列 +
3KB スタック + TCB)、ダンプタスク優先度 2(P10-1 の教訓)。

生データ: `captures/phase10/monitor_p10_4_m1.log`(PSRAM 無効 = 現行構成)、
`monitor_p10_4_m2.log`(PSRAM 有効の試行、下記のとおりハング)、
`monitor_p10_4_restore.log`(復旧確認)。

### 取得データ 1: 4 時点のヒープ実測(M1 = 現行構成、監査コード込み)

| 時点 | INTERNAL free | largest free block | min_free(最低水位) | allocated |
|---|---|---|---|---|
| 起動直後(ランチャー表示) | 70,544 | 31,744 | 59,812 | 156,120 |
| ランチャー表示中(定常) | 70,324 | 31,744 | 59,812 | 156,324 |
| mp3player 再生中 | 31,124 | **13,312** | 29,884 | 195,456 |
| midi_loopback 実行中 | 29,420 | **14,336** | 28,284 | 197,168 |
| アプリ終了後(ランチャー復帰) | 69,644 | 31,744 | 28,176 | 156,976 |

SPIRAM はいずれの時点も free=0(PSRAM 無効のため。下記データ 2)。
監査コード自体が約 5.5KB を消費しているため、main ビルドの実値は各行
+5.5KB 程度(main の `Audio_Init` 直前 free heap 156,372 に対し M1 は 150,908)。

**設計上の要点**: WASM アプリ実行中の largest free block は 13〜14KB しかなく、
9c で判明した逼迫水準(約 15KB)と一致する。ここはヒープから恒久確保しては
ならない領域である。

### 取得データ 2: sdkconfig の PSRAM 設定と PSRAM 利用コンポーネントの棚卸し

| 項目 | 実測 / 設定値 |
|---|---|
| `CONFIG_SPIRAM` | **未設定(PSRAM 無効)** — 現行 main の構成 |
| 搭載ハードウェア | 8MB octal PSRAM(M2 起動ログ: vendor 0x0d (AP)、density 64Mbit、3V、80MHz、`SPI SRAM memory test OK`) |
| 現状 PSRAM を使うコンポーネント | **ゼロ**(PSRAM 自体が無効なので当然) |
| LVGL 描画バッファ | internal。`buffer_size = LCD_H_RES * 40`、`double_buffer = true`、`task_stack_caps = MALLOC_CAP_INTERNAL` |
| WAMR プール | 静的 BSS 48KB(`s_wamr_heap`) |
| heap_init の内訳(M1) | 163 KiB (3FCC0A50) + 21 KiB + 32 KiB DRAM + 7 KiB RTCRAM |
| PSRAM 有効時の internal コスト | 163 KiB → 155 KiB(管理領域として約 8 KiB 減) |

### 取得データ 3: 16B ランダム読み書きベンチ

internal RAM(-Og ビルドのため絶対値は悲観的。比率で読むこと):

| 条件 | ns/op |
|---|---|
| ランチャーアイドル | 364.9 / 362.5 |
| mp3 再生中 | **1385.1**(1 回)、387.8(1 回) |
| midi_loopback 実行中 | 361.9 / 437.7 |
| アプリ終了後 | 363.5 |

定常は約 360〜390 ns/op で安定するが、**mp3 再生中に約 3.8 倍(1385 ns/op)へ
跳ねる回が観測された**(フラッシュ/SD アクセスとキャッシュ競合が起きる区間と
推定)。L0 キュー操作を ISR やタイマコールバック内で行う設計では、
最悪ケースがこの水準に伸びうる点を見込むこと。

**PSRAM 側のベンチは未取得**(下記の理由で中止)。

### PSRAM 有効化の試行が失敗した件(重要な発見)

`CONFIG_SPIRAM=y` + `CONFIG_SPIRAM_MODE_OCT=y` + `CONFIG_SPIRAM_SPEED_80M=y`
(Kconfig の既定で `CONFIG_SPIRAM_USE_MALLOC=y` が付く)でビルドしたところ:

- PSRAM 自体は正常に認識・初期化される(8MB、80MHz、メモリテスト OK)。
- `heap_caps_malloc(..., MALLOC_CAP_SPIRAM)` も成功する(4KB / 256KB とも
  0x3C0F.... のアドレスを返した)。一般ヒープも 8.5MB に拡大した。
- しかし **SD カード初期化の SDMMC プローブでハングし、TG1WDT による
  リブートループに陥る**。最後のログは `SDCARD: Trying SDMMC host:
  CLK=14 CMD=17 D0=16`(I(1843))で、`esp_vfs_fat_sdmmc_mount()` から戻らない。
  PSRAM 無効時はこのプローブが失敗して SDSPI へフォールバックしており、
  実際に使われるのは SPI 経路のみである。

ユーザーからリブートループの報告を受け、その場で PSRAM 有効化を撤回して
main 構成(PSRAM 無効)へ復旧した(`monitor_p10_4_restore.log`: TG1WDT
リセット 0 件、SD マウント正常、7 アプリのメニュー表示、WARN/ERROR なし)。

**この現象自体が設計判断の入力である**: 本ボードで PSRAM を使うには
SD 初期化まわりの追加調査(SDMMC プローブのスキップ、あるいは
`SPIRAM_USE_CAPS_ALLOC` への変更など)が別途必要で、ドロップイン変更ではない。

### 取得データ 4: L0 キューの配置先と最大深さの見積もり

前提: 1 イベント 16B、MIDI クロックはグリッドから直接生成するため
キューを消費しない(設計判断 4)。

| 配置案 | 現実的な上限 | 判定 |
|---|---|---|
| **internal / 静的 BSS(推奨)** | **4KB = 256 イベント** | 9c の実績(12KB 追加で WASM の linear memory 確保が失敗、4KB は問題なし)に基づく安全圏。既存の教訓「恒久物は静的確保に」(6B, 7B-fix)にも合致 |
| internal / ヒープ動的確保 | 理論上 13,312B ÷ 16 ≒ 830 イベント | **不可**。アプリ実行中の largest free block を食い潰し、WASM 起動を壊す(9c で実証済みの失敗モード) |
| PSRAM | 事実上無制限(8MB) | **現状は選択肢にならない**(PSRAM 有効化で SD 初期化がハング。レイテンシも未計測) |

256 イベントが与える先読み horizon(4/4、16 分音符グリッド、
ノート on/off で 2 イベント/音として):

| 同時発音数 | 1 小節あたり | 256 イベントで賄える長さ |
|---|---|---|
| 1 声部 | 32 イベント | 8 小節 |
| 2 声部 | 64 イベント | 4 小節 |
| 4 声部 | 128 イベント | **2 小節** |

設計候補の L2 先読み horizon「1〜2 小節先まで」は、4 声部でちょうど収まる。
より深い horizon や多声部が必要なら 8KB(512 イベント)への拡張を検討するが、
その場合は WASM linear memory 確保への影響を再検証すること(9c では 12KB で
破綻、4KB は安全、8KB は未検証)。

### 結論

- L0 キューは **internal RAM の静的 BSS に 4KB(256 イベント)** が現実的な出発点。
  PSRAM には依存しない設計とする。
- PSRAM は搭載されている(8MB octal)が、有効化には SD 初期化の別課題があり、
  本フェーズでは選択肢から外す。将来必要になった時点で再調査する。
- ISR / タイマコールバック内のキュー操作は、定常 ~360ns/op に対し
  負荷時 ~1.4µs/op まで伸びうることを見込む。

### 後片付けと現状(P10-4 時点)

- 調査コードは全て削除、sdkconfig の PSRAM 設定も撤回し、作業ツリーはクリーン。
- **実機には main(調査コードなし)のビルドが焼かれ、正常動作を確認済み**。
  P10-1〜P10-3 の計測ビルドはこれで上書きされた。

## P10-5: UART TX リアルタイムバイト割り込み挿入の PoC(2026-08-31) — 完了

### 前提(ドライバ構成の確認)

`Midi_Init` は `uart_driver_install(..., tx_buffer_size=0, ...)` で TX リング
バッファを持たない構成。IDF 5.5 のヘッダ記述どおり、`uart_write_bytes` は
「送出完了、または少なくとも TX FIFO へ押し込むまで」戻らない。ESP32-S3 の
TX FIFO は 128 バイト = MIDI 31250bps 換算で **約 41ms** ぶん。FIFO は FIFO
なので**既に積まれたバイトの前に割り込むことは原理的に不可能**であり、
0xF8 の送出遅延は「書く時点の FIFO 占有バイト数 x 320µs」に等しい。

### 方法

`src/components/midi/midi.cpp` に `#ifdef PHASE10_INTERLEAVE_TEST` ガードで
実装(検証完了後に削除済み。全差分は `captures/phase10/p10_5_test_code.patch`)。
3 モードを 120 秒ずつ自動で切り替えて比較した:

| モード | 内容 |
|---|---|
| **M0** | クロックのみ(ノート送出なし)= P10-3 相当のベースライン |
| **M1** | 素朴実装。ノート 3 バイトを 1 回の `uart_write_bytes` で送出。0xF8 はタイマから即送出 |
| **M2** | ペーシング実装。ノートを 1 バイトずつ送り、各バイト後に `uart_wait_tx_done` で FIFO を空にする。0xF8 はバイト境界で注入 |

- ノートは 10ms 間隔で `[0x90, note, 0x40]`(note は 0..127 巡回)。
- クロックは P10-3 と同じ絶対時刻グリッドのワンショット連鎖(20833µs)。
- 受信側は `rx_task` の打刻点で、(a) 0xF8 の間隔統計(9c/P10-3 と同一バケット)、
  (b) **0xF8 を取り除いた列が送信列と一致するかを検証する状態機械**を回す。
- ジッタの帰属先を切り分けるため 2 つのプローブを追加:
  **(A)** 0xF8 を書く直前の TX FIFO 占有量(`uart_ll_get_txfifo_len`)、
  **(B)** UART RX イベント 1 件が運ぶバイト数(打刻を共有するバイト数)。

生データ: `captures/phase10/monitor_p10_5_lb2.log`(初回ループバック)、
`monitor_p10_5_attr.log`(プローブ追加後のループバック、下表の出典)、
`monitor_p10_5_slmk3.log`(SL MK3 セッション)、`monitor_p10_5_restore.log`(復旧確認)。

### 結果 1: ノート列の完全性(確認内容 1(a))

| モード | 受信 OK メッセージ数 | エラー | waiterr |
|---|---|---|---|
| M1 | 12,021 | **0** | 0 |
| M2 | 12,022 | **0** | 0 |

**0xF8 を挟んでもノートメッセージは 1 バイトも欠落・化けしない。**
0xF8 を取り除いた列は送信列と完全一致した(2 セッション合計 24,043 メッセージ)。

### 結果 2: 0xF8 の間隔統計(確認内容 1(b))

| モード | RX n | 外れ値 | mean(µs) | σ(µs) | min/max(µs) |
|---|---|---|---|---|---|
| M0 | 5,770 | 0 | 20833.0 | **16.3** | 20697 / 20971 |
| M1 | 5,770 | 0 | 20833.0 | **1185.7** | 19472 / 24957 |
| M2 | 5,770 | 0 | 20833.4 | **1190.3** | 19584 / 25073 |

ノート送出があると σ が約 70 倍に悪化する。**しかし M2(ペーシング)は
M1(素朴)を改善しなかった。** この一見不可解な結果を下記プローブで切り分けた。

### 結果 3: ジッタの帰属(プローブ A/B)

**(A) 0xF8 を書く瞬間の TX FIFO 占有量**(= 線に出るまで待たされるバイト数):

| モード | 平均 | 最大 | 内訳 [0 / 1 / 2 バイト] | 換算遅延 |
|---|---|---|---|---|
| M0 | 0.00 | 0 | [5771, 0, 0] | 0µs |
| M1 | **0.05** | **2** | [5535, 164, 72] | 平均 16µs / 最悪 640µs |
| M2 | **0.00** | **0** | [5771, 0, 0] | **常に 0µs** |

**(B) UART RX イベント 1 件が運ぶバイト数**(= 打刻を共有するバイト数):

| モード | 1 バイト | 3 バイト | 4 バイト |
|---|---|---|---|
| M0 | 5,771 | 0 | 0 |
| M1 | 1,363 | 7,614 | **4,408** |
| M2 | 1,336 | 7,588 | **4,435** |

**決定的な証拠**: M2 は TX FIFO 占有量が全 5,771 回とも 0(送信側の待ちが
証明可能にゼロ)であるにもかかわらず、RX 側の σ は M1 と同一(1190 vs 1186µs)。
送信側に遅延が存在しないのに同じジッタが観測される以上、
**σ 1.19ms は送信ジッタではなく受信側の計測アーティファクト**である。

原因は `rx_task` が 1 回の UART イベントで届いた複数バイトに**同一の
タイムスタンプ**を付けること。M0 では全イベントが 1 バイトなので σ 16µs だが、
ノートがあると 3〜4 バイトがまとめて届き、0xF8 の見かけの時刻が最大 4 バイト分
(≈1.3ms)ずれる。SL MK3 セッション(ループバック非接続)でも TXOCC は
M1 平均 0.05/最大 2、M2 常に 0 と同一値で再現した。

### 結果 4: SL MK3 実機での確認(確認内容 2)

自機 MIDI OUT → SL MK3 MIDI IN に接続し、各モード開始時に MIDI Start(0xFA)を
送出する版で、ユーザーが 4 分間(M1/M2 の両方を通過)目視確認した。

> **「全くちらつきはなく、テンポ表示は安定していました」**(ユーザー報告)

10ms 間隔のノート送出を受けながら、クロック検知テンポは 120 BPM で安定した。

### 結論(設計判断 5 の可否)

- **設計判断 5「システムリアルタイムバイトを他メッセージの途中に割り込ませる」は
  ESP32 の UART ドライバ構成で成立する。** バイト列の完全性は完璧(24,043
  メッセージでエラー 0)、実機受信側(SL MK3)のテンポ検知も安定。
- **TX FIFO 直叩きは不要。`uart_write_bytes` で足りる。** 実測の挿入遅延は
  平均 16µs・最悪 640µs(2 バイト)で、MIDI 1 バイト時間 320µs と同オーダー。
  TX リングバッファ(`tx_buffer_size>0`)も不要(むしろリングバッファを挟むと
  割り込み地点の制御が効かなくなるため、現行の `tx_buffer_size=0` が適切)。
- **ただし条件付き**: FIFO は 128 バイト = 41ms ぶんある。SysEx(Phase 8c で
  302 バイトを実測)のような大きなバーストを 1 回の `uart_write_bytes` で
  流し込むと、その後の 0xF8 は最大 41ms 待たされる。
  **ポート層の送出規律**: 大きなメッセージは一括で FIFO に流し込まず、
  M2 のように小さく分割して書き、バイト境界ごとにリアルタイムキューを
  確認すること。小さなメッセージ(3〜4 バイト)なら一括で問題ない。
- **録音打刻(`time_us_to_tick`)への申し送り**: 受信バイトのタイムスタンプは
  UART イベントのバッチ境界までしか正確でない(連続受信時は 3〜4 バイトが
  同一時刻を共有し、最大 ≈1.3ms の誤差)。ボーレートが既知なので、
  N バイトのイベントの i 番目の到着時刻を **`T - (N-1-i) x 320µs`** と
  補正すれば復元できる。この補正は L0/L1 の入力経路に入れる価値がある。
  (P10-3 で申し送った「送信グリッド精度と受信打刻精度を区別せよ」を
  定量的に裏付けた形。)

- 実機には main(調査コードなし)のビルドを焼き直し、正常起動を確認済み。
