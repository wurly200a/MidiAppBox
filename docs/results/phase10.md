## P10-1: I2S 再生位置(消費済みサンプル数)の取得可能性 【go/no-go ゲート】(2026-08-30) — **判定: go**

### 方法

`src/components/audio/audio.cpp` に `#ifdef PHASE10_I2SPOS_TEST` ガードで
調査コードを実装(検証完了後に削除済み。削除前の全差分は
`captures/phase10/p10_1_test_code.patch` に保存。P10-2 で再利用する)。

- **(b) on_sent コールバック**: `i2s_channel_register_event_callback` で TX の
  `on_sent` を登録(enable 前の REGISTERED/READY 状態でのみ登録可能な点に注意)。
  ISR 内で `esp_timer_get_time()` を打刻し、(累計送信バイト, us) から
  コールバック間隔 dt の逐次統計(sum/sumsq/min/max/8バケットヒストグラム)と、
  3点窓の中点補間誤差 err = t1 − (t0+t2)/2(バイト増分が等しい3点のみ)を
  整数演算のみで集計。10 秒毎に専用タスク(静的スタック 3KB)がシリアルへダンプ。
- **(a) 書き込み累計**: `Mp3Player::i2s_write` に累計バイト・呼び出し回数・
  ブロック時間(min/max/avg)の計測を追加。
- 静的追加は合計約 3.7KB(スタック 3072B + 統計構造体 + TCB)で、9c の教訓に
  従い 4KB 以下に収めた。ヒープへの影響は下記「ヒープ確認」参照。
- CMakeLists.txt に `PRIV_REQUIRES esp_timer` を一時追加(削除済み)。

生データ: `captures/phase10/`(.gitignore 対象)
- `monitor_p10_1.log`: run 1(計測ビルド、ダンプタスク優先度 4)
- `monitor_p10_1_baseline.log`: run 2(対照: 調査コード無効のベースライン)
- `monitor_p10_1_run3.log`: run 3(計測ビルド、ダンプタスク優先度 2)

### 取得データ 1: 粒度

| 項目 | 実測値 |
|---|---|
| DMA バッファ 1 個 | 960 バイト = 240 フレーム(既定 `dma_frame_num=240`、16bit ステレオ) |
| 時間換算 @44.1kHz | 5442.2µs(理論値 240/44100 = 5442.18µs と一致) |
| DMA リング全体 | 6 ディスクリプタ × 960B = 5760B ≒ 32.7ms |

**重要な定性結果**: `on_sent` は**データ未供給時(無音)もフリーランで発火し続ける**
(`auto_clear` 有効時、ドライバがゼロを送出し続けるため。IDF ヘッダの記述どおり)。
起動直後から一切 write しなくても 960B/5442.2µs で単調増加のサンプルカウントが
得られる。Clock Authority のレートマスターとして理想的な性質。

### 取得データ 2: コールバック打刻間隔の統計(E1 と同形式)

| 区間 | n | 平均(µs) | σ(µs) | min/max(µs) | ヒストグラム(中心バケット 5400-5499 外の件数) |
|---|---|---|---|---|---|
| run1 アイドル 180s | 33,136 | 5442.2 | 0.8 | 5393 / 5492 | 2(5300-5399) |
| run1 全体(metronome+mp3+タッチ込み 350s) | 64,439 | 5442.2 | 1.0 | 5380 / 5504 | 9 |
| run3 全体(mp3 46s+metronome 込み 190s) | 34,977 | 5442.2 | 0.6 | 5425 / 5460 | **0(全数が中心バケット)** |

理論値 5442.18µs からの偏差は平均レベルでゼロ(表示精度 0.1µs 内)、
ジッタは σ 0.6〜1.0µs、最悪でも ±62µs。09c の esp_timer periodic
(σ83〜86µs、min/max −635〜+1224µs)より**約2桁タイト**。
I2S DMA 割り込みが高優先度で処理されているため。

### 取得データ 4: 既存経路との干渉有無(A/B/A 対照で確認)

3 回の実機セッションで切り分けた:

1. **run 1(計測ビルド、ダンプタスク優先度 4)**: metronome のクリックは正常
   (ユーザー所感「いつもどおり」)。**mp3player は前半に断続的な音切れ**を
   ユーザーが聴取。ログ上、音切れ区間はユーザーのタッチ操作バースト
   (4 秒間に 33 イベント、タッチログ大量出力)と重なり、書き込みレートも
   公称 176.4KB/s を下回る窓があった(173〜175KB/s)。
2. **run 2(ベースライン: 調査コード無効、再生中無操作)**: 音切れなし、
   metronome も Phase 10 実施前と同じ(ユーザー確認)。
3. **run 3(計測ビルド、ダンプタスク優先度を 4→2 に修正、再生中無操作)**:
   **音切れなし、metronome もベースラインと同じ**(ユーザー確認)。mp3 再生中の
   書き込みレートは 176.6KB/s と公称に一致し、飢餓の痕跡なし。WARN/ERROR なし。

結論: **on_sent コールバック+カウンタ自体は可聴・可測の干渉を起こさない**
(run 3 で実証)。run 1 の音切れは調査の足場側の問題
(統計ダンプタスクの優先度が audio_player タスクの 3 より高かった)と
再生中のタッチ操作(ログ大量出力)の複合であり、いずれも本設計
(Clock Authority)には持ち込まれない。教訓: **音声再生と共存する常駐タスクは
audio_player(優先度 3)より低い優先度にすること**。

### (a) 書き込み累計方式の評価

- 累計カウント自体は成立する(run3: metronome 10 秒窓で 221,040B = 20 クリック
  × 11,052B、120bpm と正確に一致)。
- ただし **write が発生している間しかカウントが進まない**(アイドル・クリック間の
  無音区間では DAC はゼロを消費し続けるが、書き込み累計は止まる)。
- ブロッキング write の戻りタイミングは消費と疎結合(ブロック時間 実測
  min 9µs / max 44.7〜51.6ms。DMA に空きができるまで待つため、MP3 の
  デコードチャンク単位で数十 ms ブロックする)。
- よって (a) 単独ではレートマスターに使えない。**(b) を採用**。

### ヒープ確認(9c 教訓のチェック)

| 時点 | free heap | largest free block |
|---|---|---|
| 起動直後(調査コード込み) | 71,300 | 31,744 |
| WASM アプリ実行中(調査コード込み) | 33,804 | 14,336 |

調査コード(静的 ~3.7KB)追加後も WASM 全アプリが正常起動
("allocate linear memory failed" なし)。アプリ実行中の largest block
約 14KB は 09c で判明済みの逼迫水準と同等で、悪化なし。

### go/no-go 判定: **go**

- (b) で単調増加のサンプルカウントが取得でき、無音時もフリーランで継続する。
- 線形補間後の時刻対応誤差は負荷込み最悪 ±62µs で、基準 ±500µs を
  1 桁近い余裕で満たす。
- 既存の click / MP3 再生経路への干渉なし(A/B/A 対照で確認)。

設計候補「オーディオ出力のサンプルカウントをレートマスターとする Clock
Authority」との矛盾なし。補間誤差が MIDI 1 バイト時間(320µs)より
十分小さいため、(sample_count, us) ペアの線形補間で系内時刻変換が成立する。
