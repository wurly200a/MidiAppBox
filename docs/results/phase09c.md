## 実機検証で判明した副次的な問題(WASM 側メモリ不足)

E2 の当初実装(`TxArmRecord[512]`、`uint64+uint32*2+int32*2` で約12KB)を
`midi.cpp`(native、ESP32 側)に追加したところ、`midi_loopback.wasm`(E1 改修版)が
実機でのみ **`WASM module instantiate failed: allocate linear memory failed`**
に失敗した(Linux ホストでは同一の WAMR プール 48KB でも成功)。

切り分けの結果、原因は WASM アプリ側の静的データ量ではなく、**E2 用に
`midi.cpp` へ追加した 12KB の静的バッファが ESP32 の一般ヒープ(WAMR プールとは
別領域)を圧迫していたこと**だった(`heap_init` の「RAM available for dynamic
allocation」領域が 12KB 少なく報告されていた。当該バッファを外すと同一の
`.wasm` がそのまま起動した)。実機のヒープはこの時点で largest free block が
約15KBしかなく、Linux ホストより著しく逼迫していた。

対処として E2 のレコードを軽量化した(タイムスタンプを `u64`→`u32`、
戻り値を `int32_t`→`int16_t`、件数を 512→250)。`sizeof(TxArmRecord)` は
24→16 bytes、総量は約12KB→約4KBに削減し、以降は問題なく起動した。
また、E1 側も当初計画していた生サンプル配列(`[u16; 6000]`、約12KB)を
やめ、ヒストグラムから近似する中央値と、公称値ベースの固定閾値による
逐次(Welford)ロバスト統計に設計変更した(詳細は `lib.rs` のコメント参照)。
静的メモリの増分は数百バイトに収まっている。

**教訓(`docs/lessons.md` に追記)**: WAMR プールだけでなく native 側の
一般ヒープも WASM の linear memory 確保に影響しうる。大きな静的バッファを
native 側に追加する際は、WAMR プールの空きだけでなく `heap_init` の
「RAM available for dynamic allocation」・実機の largest free block も
確認すること。

## E2 の結果(再アーム区間ごとのクロック送出数)

3回のセッション合計 750 レコード中、**747件(99.6%)が厳密に 23 または 24**
(23発: 457件、24発: 290件)。残り3件(7, 10, 25)はいずれも START/STOP
境界(セッション開始直後・終了直前)の過渡的な区間で、境界効果として妥当。

23発の割合(約61%)は、E1 側の外れ値発生率(outN / 総拍数、約61〜64%相当)と
よく一致しており、**送信側(esp_timer による24ppqnクロック生成)ですでに
クロックが欠落していること**が直接確認できた。受信側(UART RX・
`hostapi_midi_recv` 経由の取りこぼし)が主要因である証拠はない
(欠落は送信のごく手前、`clock_timer_cb` が呼ばれる前の再アームの瞬間に
起きている)。

## 「有力仮説」節の予測値と実測値の対応表

| 予測項目 | 予測値 | 実測値 | 判定 |
|---|---|---|---|
| 欠落発生時のクロック間隔(外れ値) | 約41,674µs | 41,489〜41,752µs(24サンプル、中心値は予測とほぼ一致) | 支持 |
| 欠落を1回含む24クロック窓の見かけBPM | 約115.2 | 114-116バケットに集中(3586/4288/3643件)、中間値(116-119.5)はほぼ0 | 支持 |
| 欠落を含まない窓の見かけBPM | 約120.0 | 119.5-120.5バケットに集中(2163/2603/2584件) | 支持 |
| 1拍あたりのクロック数 | 24または23の二値 | TXLOGの99.6%が23/24の二値(境界の3件を除く) | 支持 |
| 定常区間(欠落を除く)のクロック間隔 | 20833µs付近、σは小さい | ロバスト平均20834〜20836µs(公称比+1〜+3µs)、σ=83〜86µs | 支持 |

**仮説の可否判定: 支持する。** `Midi_NotifyBeatFired()` が毎拍
`esp_timer_stop()`→`esp_timer_start_periodic()` で位相をリセットし、
120bpm では24発目の発火(499,992µs後)と次拍の再アーム(500,000µs後)の
マージンがわずか8µsしかないため、クリックスケジューラのジッタで
確率的に24発目が切り落とされる、という仮説どおりの挙動が送受信双方の
データで一貫して確認された。

## E3 の結果(対照実験: 位相リセットの無効化)

`Midi_NotifyBeatFired()` を「周期(interval_us)が直前と変わらなければ
再アームしない」変種に変更し、同一条件(120bpm・120秒・3回)で測定した。

| 試行 | 総クロック数 | 外れ値件数(outN) | 114-116 | 119.5-120.5 | その他 | 除外後平均 | TXLOGレコード数 |
|---|---|---|---|---|---|---|---|
| 1 | 6947 | **0** | 0 | 6916 | 0 | 20834 | 2 |
| 2 | 5982 | **0** | 0 | 5951 | 0 | 20837 | 2 |
| 3 | 6189 | **0** | 0 | 6157 | 1 | 20838 | 2 |

**E1 との差分**: 外れ値が3回とも完全に0件になり(E1/E2では155〜185件)、
BPM分布の115付近のピークが完全に消失、ほぼ全windowが119.5-120.5に収束した
(その他バケットも1件のみで無視できる)。TXLOGのレコード数が2件のみ
(初回アームと STOP 直前の最終確定のみ)であることも、「周期が変わらない
限り再アームしない」設計どおりに動作したことを裏付ける。定常区間の
ロバスト平均(20834〜20838µs、公称比+1〜+5µs)は E1/E2 とほぼ同一で、
系統的なタイマー周期の丸め等が別途悪影響していないことも確認できた。

以上により、**毎拍の位相リセット(stop/start_periodicによる再アーム)が
クロック欠落の直接の原因であること**が対照実験で定量的に実証された
(仮説採用、恒久修正は行わない。E3コードは検証後に削除し main の挙動は
測定前と同一に戻した)。

## 回帰確認

最終ビルド(検証専用コードを全て削除した状態)で実機の全 WASM アプリ
(demo / bars / touch_demo / mp3player / clicktest / metronome / midi_loopback)を
順に起動・操作・終了し、`free heap` が起動時と一致(mp3player のみ
-44Bの小さな差、過去Phaseでも見られた既知の挙動)、WARN/ERROR なしを確認。
同一の `.wasm`(E1改修版含む)は Linux ホストでもエラーなく起動・終了する
ことを確認済み(`app_init=0`、`app stopped`、残留プロセスなし)。

## 後続のアーキテクチャ刷新フェーズへの申し送り事項

1. **根本原因は確定した**: `Midi_NotifyBeatFired()` の毎拍位相リセットが
   120bpm・24ppqnにおいて実質マージン8µsという「ほぼゼロ」の余裕しかなく、
   クリックスケジューラの数百µs〜ms級ジッタで確率的にクロックを
   欠落させている(約61%の拍で発生。E1/E2の全指標・E3の対照実験で
   定量的に確認済み)。
2. **E3の対策は暫定検証専用**であり、テンポ変更時の位相制御・小節同期の
   設計を欠く(「周期が変わらなければ再アームしない」だけでは、
   テンポ変更の瞬間に毎回大きな位相ジャンプが起きる可能性が高い)。
   ホスト側に音楽時間軸(テンポマップ・拍/小節カウンタ)を持たせ、
   MIDI Clock を「前回の発音時刻からの相対的な再アーム」ではなく
   「絶対時刻グリッド上の次クロック時刻」に基づいて生成する設計
   (毎拍のstop/start再アーム自体をやめる)を検討すべき。
3. **副次的な教訓(メモリ)**: ESP32側では WAMR プール(48KB)とは別に、
   native側の静的メモリ追加も一般ヒープを圧迫し WASM の linear memory
   確保失敗を誘発しうる(本フェーズで largest free block が実測約15KBまで
   逼迫していることが判明)。今後 native 側に大きな検証用/恒久バッファを
   追加する際は、事前に一般ヒープの余裕(`heap_init` ログ・
   `heap_caps_get_largest_free_block`)も確認すること。
4. 120bpm 以外のテンポでは `period_ms` の整数丸めに起因する別の系統誤差が
   予想される(本フェーズのスコープ外、次回計測時に確認推奨)。
5. Song Position Pointer 等の高度な MIDI 同期は引き続きスコープ外。
